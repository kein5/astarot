# リリースノートの書式

GitHub のリリースの本文にするノートを、バージョンごとに `docs/release-notes/<バージョン>.md` に置きます。0.5.0 からこの書式で書きます。0.4.0 までのノートは、この書式に組み替えません。

`CHANGELOG.md` は、コミットからすべての変更を並べる記録です（`tools/changelog.py`）。リリースノートは、更新するかどうかを決めるための文章で、手で書きます。両方が食い違ったときは、`CHANGELOG.md` を先に直してから、ノートを直します。

## 全体の形

冒頭に2〜4行の要約を置き、大見出しを次の2つに分けます。

1. `## 利用者に関係のある変更`
2. `## 内部の変更`

要約には、このバージョンで利用者に起きる大きな変化を書きます。プライバシーやセキュリティの修正があれば、要約でも触れて、その節へ案内します。

## 利用者に関係のある変更

新しい機能、使い勝手の改善、不具合の修正、互換性の変化、更新するときに利用者がすることを書きます。

- 平易な言葉で書きます。内部の実装の名前（クレート、ライブラリ、エンドポイントなど）は、利用者がすることに関わるときだけ書きます。
- 画面の文言は `locales/ja.yml` の表記のまま引きます。設定の場所は「設定」→「ページ」→「項目」の形で書きます。
- 機能ごとに `###` の節を作ります。節の最後に、次の2つを置きます。
  - `### 更新するときの注意`：前の正式版から更新するときにすること。互換性がなくなった点もここに書きます。項目ごとに `####` で分けます。
  - `### 既知の問題`：制限と、公開する前に確かめられなかったこと。
- 内部の変更が利用者に見える形で現れるとき（データの送り先が変わるなど）は、見える部分をこちらに書きます。

## 内部の変更

実装の置き換え、依存の更新、開発の基盤、ライセンスやドキュメントの整備を書きます。

- 専門用語のままで構いません。
- 1項目を箇条書きの1行にし、末尾に PR の番号を付けます（例：`（#341）`）。Issue の番号ではなく、変更を入れた PR の番号です。
- 最後に、`CHANGELOG.md` へのリンクを置きます。

## 書くときの注意

- 対象は、前の正式版のタグから、リリースするコミットまでにマージした PR です。漏れがないかは、`python tools/changelog.py print` の結果と、`git log --first-parent` の PR の一覧で確かめます。
- 人の名前、担当、開発に使った PC の環境は書きません。
- 読み手の PC を「この PC」のように開発者の側から指す言い方はしません。
- 計測した値は、条件とあわせて書きます。

## リリースの下書きとの関係

「Prepare verified VRCT-VOX release draft」が作る下書きの本文は、`tools/changelog.py` の骨組み（Highlights、Upgrade Notes、Known Issues と変更の一覧）です。公開する前に、本文をこの書式のノートに差し替えます。手順は [CONTRIBUTING.md](../../CONTRIBUTING.md#changelog-and-releases) と [配布候補とリリース下書き](../voice-stack/release-candidates.md) にあります。
