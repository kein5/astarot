# ASTAROT functional specification

[日本語版](#astarot-機能仕様書日本語版)

The entry point to the documents that describe ASTAROT's features, API, data and promised behavior. Every document can be reached from here.

The product's purpose and users are in `PRODUCT.md`, its look and operation in `DESIGN.md`, and how development works in `AGENTS.md` and `docs/development.md`. Under the policies those documents set, this specification describes "what works how, now".

The Python implementation up to 0.5.x ([`src-python/controller.py`](https://github.com/kein5/astarot/blob/v0.5.2/src-python/controller.py)) was removed in 0.6.0, so read it at a 0.5.x tag |

## Update rules

- The three lists in `reference/` are generated by `tools/spec_catalog.py`. Do not edit them by hand. The inputs are `tools/spec_core_catalog.json`, which the core (`native/core`) writes out, the validation expressions of the settings keys (`keys()` in `native/core/src/config/schema.rs`), and the UI code.
- The component map in `reference/` (`component-map.md`) is generated by `tools/component_map.py` from `tools/component_map.toml`, the only place where its names and roles are edited. Do not edit the page by hand. After editing the data file, run `mise run component-map`.
- When you change the core's endpoints, notifications, error codes or settings keys, run `mise run spec` in the same change to rebuild the JSON and the lists. It runs these two commands:

  ```sh
  VRCT_SPEC_CATALOG_WRITE=1 cargo test --manifest-path native/core/Cargo.toml --test spec_catalog
  python tools/spec_catalog.py --write
  ```

- When the lists are out of date, these two tests fail:
  - The core test `native/core/tests/spec_catalog.rs` checks that the JSON matches the core. It runs in the `core-integration` CI job.
  - `tests/devtools/test_spec_catalog.py` in `python tools/dev.py check` checks that the lists match what is built from the JSON and the UI code.
- Fix the hand-written documents in the same pull request as the change that altered the behavior. Keep each document small and about one feature, do not write the same thing in two places, and connect documents with links.
- When you find a statement that disagrees with the implementation, check which one is right. If you cannot decide, write it in [Open issues](open-issues.md).
- Give the location of a file or function by file name and name, not by line number, because line numbers change quickly.

## Ideas this specification adopted

To decide how to structure the documents, we looked at primary sources on how to make specifications and API documents (2026-11-02; the research notes are kept locally in `~/research/functional-spec-practices/`). What we adopted, and the sources, are listed below.

| Idea | Its form in this specification | Source |
|---|---|---|
| Arrange reference documents to match the structure of the product, and write only facts in them. Do not mix them with explanations or procedures | The lists (reference) are separate from the rules and scenario documents | [Diátaxis: Reference](https://diataxis.fr/reference/) |
| An API reference generated from the product's code stays faithful to the code. But a generated reference alone is not enough as documentation | Endpoints, error codes and settings keys are generated; the protocol and the behavior are written by hand | [Diátaxis: Reference](https://diataxis.fr/reference/), [LSP 3.17 Meta Model](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/) |
| The most common documentation problems are being ambiguous, incomplete, wrong or out of date | Generation and checks keep the lists from going out of date, and undecided points are written separately in the open issues | [Uddin & Robillard, How API Documentation Fails (IEEE Software, 2015)](https://www.cs.mcgill.ca/~martin/papers/ieeesw2015.pdf), [Aghajani et al., Software Documentation Issues Unveiled (ICSE 2019)](https://emadpres.github.io/pdfs/icse2019.pdf) |
| Split a message convention into a common base protocol (the form of messages, the difference between requests and notifications, the form of errors) and descriptions of the individual messages. Notifications get no response | Split into the [IPC protocol](ipc-protocol.md) and the lists, with requests and notifications kept apart | [LSP 3.17 Base Protocol](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/), [JSON-RPC 2.0](https://www.jsonrpc.org/specification), [AsyncAPI 3.0.0](https://www.asyncapi.com/docs/reference/specification/v3.0.0) |
| Put rules that span several components in one place | [Cross-cutting behavior](cross-cutting.md) was set up | [arc42 §8 Crosscutting Concepts](https://docs.arc42.org/section-8/) |
| For runtime flows, pick representatives from the important scenes, the interactions with the outside, startup and shutdown, and errors. Writing many of them is not what matters | [Sequences](sequences.md) is limited to six scenes and includes the error branches | [arc42 §6 Runtime View](https://docs.arc42.org/section-6/), [C4 Dynamic diagram](https://c4model.com/diagrams/dynamic) |
| A specification includes real usage scenarios and open issues. An overview that works as a table of contents comes first | [Use cases](use-cases.md), [Open issues](open-issues.md), the list on this page | [Spolsky, Painless Functional Specifications Part 2](https://www.joelonsoftware.com/2000/10/03/painless-functional-specifications-part-2-whats-a-spec/) |
| Large documents do not get updated. Small, split documents have a chance of being updated | Split into small documents per feature, reachable from this page | [Nygard, Documenting Architecture Decisions](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions) |
| Handle documents with the same tools as code (Git, review, automated tests), so that a change without documentation can be stopped | The check of the lists is part of `check` | [Write the Docs: Docs as Code](https://www.writethedocs.org/guide/docs-as-code/) |
| Keep a contract with tests that check the promises of the interaction with the other side | Each [contract](contracts.md) names the tests that check it | [Fowler, ContractTest](https://martinfowler.com/bliki/ContractTest.html), [Robinson, Consumer-Driven Contracts](https://martinfowler.com/articles/consumerDrivenContracts.html) |

What the research could not settle:

- We found no study that measured how much generation or contract tests reduce the drift of documents. The decisions above rest on the claims of the primary sources and on studies of documentation problems.
- The primary source of the use case format (Cockburn's template) could not be obtained. The use cases take a simple form: the trigger, the main flow, what happens when it goes wrong, and what is involved.

## 更新の決まり

- `reference/`の3つの一覧は`tools/spec_catalog.py`が生成する。手で編集しない。入力は、中核（`native/core`）が書き出した`tools/spec_core_catalog.json`、設定キーの検証の式（`native/core/src/config/schema.rs`の`keys()`）、UIのコードである。
- `reference/`の構成図（`component-map.md`）は、`tools/component_map.py`が`tools/component_map.toml`から生成する。構成図の名前と役割を直すのは、このデータファイルだけである。ページは手で編集しない。データファイルを直したら`mise run component-map`を実行する。
- 中核のエンドポイント、通知、エラーコード、設定キーを変えたら、同じ変更で`mise run spec`を実行し、JSONと一覧を作り直す。中身は次の2つである。

  ```sh
  VRCT_SPEC_CATALOG_WRITE=1 cargo test --manifest-path native/core/Cargo.toml --test spec_catalog
  python tools/spec_catalog.py --write
  ```

- 一覧が古いと、次の2つの試験が落ちる。
  - 中核の試験`native/core/tests/spec_catalog.rs`: JSONが中核と一致するかを確かめる。CIの`core-integration`で流れる。
  - `python tools/dev.py check`の`tests/devtools/test_spec_catalog.py`: 一覧がJSONとUIのコードから作ったものと一致するかを確かめる。
- 手書きの文書は、振る舞いを変えた変更と同じプルリクエストで直す。文書は機能ごとに小さく保ち、同じことを2か所に書かず、リンクでつなぐ。
- 実装と食い違う記述を見つけたら、どちらが正しいかを確かめる。決められなければ[未決事項](open-issues.md)に書く。
- ファイルや関数の場所は、行番号ではなくファイル名と名前で書く。行番号はすぐに変わるためである。

## この仕様書が採り入れた考え方

文書の構成を決めるために、仕様書・API文書の作り方の原典を調べた（2026-11-02。調査の記録は手元の`~/research/functional-spec-practices/`にある）。採り入れたことと、その出典は次のとおり。

| 考え方 | この仕様書での形 | 出典 |
|---|---|---|
| 参照の文書は製品の構造に合わせて並べ、事実だけを書く。説明や手順と混ぜない | 一覧（参照）と、決まり・シナリオの文書を分けた | [Diátaxis: Reference](https://diataxis.fr/reference/) |
| APIの参照は製品のコードから生成すると、コードに忠実なまま保てる。ただし生成した参照だけでは文書として足りない | エンドポイント、エラーコード、設定キーは生成し、プロトコルと振る舞いは手で書いた | [Diátaxis: Reference](https://diataxis.fr/reference/)、[LSP 3.17のMeta Model](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/) |
| 文書の問題で多いのは、あいまい、不完全、誤り、古い、である | 生成と検査で古くなるのを防ぎ、未決のことは未決事項に分けて書いた | [Uddin & Robillard, How API Documentation Fails (IEEE Software, 2015)](https://www.cs.mcgill.ca/~martin/papers/ieeesw2015.pdf)、[Aghajani et al., Software Documentation Issues Unveiled (ICSE 2019)](https://emadpres.github.io/pdfs/icse2019.pdf) |
| メッセージの規約は、共通の基本プロトコル（メッセージの形、要求と通知の違い、エラーの形）と、個々のメッセージの説明に分ける。通知には応答を返さない | [IPCプロトコル](ipc-protocol.md)と一覧に分け、要求と通知を区別した | [LSP 3.17 Base Protocol](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/)、[JSON-RPC 2.0](https://www.jsonrpc.org/specification)、[AsyncAPI 3.0.0](https://www.asyncapi.com/docs/reference/specification/v3.0.0) |
| 複数の構成要素にまたがる決まりは1か所にまとめる | [横断的な振る舞い](cross-cutting.md)を設けた | [arc42 §8 Crosscutting Concepts](https://docs.arc42.org/section-8/) |
| 実行時の流れは、重要な場面、外部とのやり取り、起動と停止、エラーから代表を選んで書く。数を多く書くことは重要ではない | [シーケンス](sequences.md)を6場面に絞り、エラーの分岐を入れた | [arc42 §6 Runtime View](https://docs.arc42.org/section-6/)、[C4 Dynamic diagram](https://c4model.com/diagrams/dynamic) |
| 仕様には実際の利用場面と、未決事項を書く。冒頭に目次となる全体像を置く | [ユースケース](use-cases.md)、[未決事項](open-issues.md)、このページの一覧 | [Spolsky, Painless Functional Specifications Part 2](https://www.joelonsoftware.com/2000/10/03/painless-functional-specifications-part-2-whats-a-spec/) |
| 大きな文書は更新されない。小さく分けた文書なら更新される見込みがある | 機能ごとの小さな文書に分け、このページから引けるようにした | [Nygard, Documenting Architecture Decisions](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions) |
| 文書をコードと同じ道具（Git、レビュー、自動テスト）で扱い、文書のない変更を止められるようにする | 一覧の検査を`check`に入れた | [Write the Docs: Docs as Code](https://www.writethedocs.org/guide/docs-as-code/) |
| 契約は、相手とのやり取りの約束を確かめるテストで守る | [契約](contracts.md)ごとに確かめているテストを書いた | [Fowler, ContractTest](https://martinfowler.com/bliki/ContractTest.html)、[Robinson, Consumer-Driven Contracts](https://martinfowler.com/articles/consumerDrivenContracts.html) |

調べても分からなかったこと:

- 生成や契約テストで文書のずれがどれだけ減るかを測った研究は見つからなかった。上の判断は、原典の主張と、文書の問題を調べた研究に基づく。
- ユースケースの書式の原典（Cockburnのテンプレート）は取得できなかった。ユースケースは、きっかけ、主な流れ、うまくいかないとき、関係するもの、の簡単な形にした。
