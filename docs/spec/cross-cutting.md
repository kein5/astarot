# Cross-cutting behavior

[日本語版](#横断的な振る舞い日本語版)

This file collects the rules that span several features (what arc42 calls "Crosscutting Concepts"). The documents for individual features refer to the rules here instead of repeating them.

## Error handling

Errors reach the UI by 4 paths.

| Path | Shape | Examples | How the UI shows it |
|---|---|---|---|
| A 400 response to a request | `{"status": 400, "result": {"error_code", "message", "data", …}}` | Settings validation, a rejected API key | `errorHandling_Backend` (`src-ui/logics/_useBackendErrorHandling.ts`) restores the value on screen from `data` and shows a translated string in a notification |
| A 400 notification from the sidecar | The same shape, arriving at `/run/error_…` and similar endpoints | Not enough VRAM, no input device, a translation engine limit | Same as above. When a feature that was on was turned off automatically, the display of its switch is also reverted |
| A recognition error notification | `{error_code, stage, source, message, recoverable}` in a 200 `/run/transcription_recognition_error`. When a cloud engine returned a reason for the failure, the core adds `cause` (`TRANSCRIPTION_API_AUTH_FAILED`, `_RATE_LIMITED`, `_TIMEOUT`, `_SERVER_ERROR`). `error_code` stays `ASR_ERROR` | A speech recognition failure | Kept in the message log as a system message. Shows the `backend_errors` string for `cause` if there is one, and otherwise the `backend_errors.<code>` string; if `<code>_mic` or `<code>_speaker` exists, the one that matches `source` is used. If there is no string, shows the English `message` |
| A per-feature error state | `{"error_code": …}` with 409 and other statuses | TTS, RVC, speech server, model download, real-time speech recognition | The status field of each settings screen shows the string for `error_code` |

- On 404, 423, 500 and send failures, ordinary controls release their wait and go back to the last confirmed value. On 500 the state is read again from the matching read endpoint. No automatic resending of writes and no release of a wait based on time alone are added. For languages, voice and model downloads, which have their own matching, and for what happens when the sidecar exits, see [IPC protocol](ipc-protocol.md#失敗した要求の待機を解除する).
- For a 400 response to turning OBS on, changing its port or the WebSocket host change that comes with them, `data` holds the value before the change of the setting that made the request. The UI also picks the setting to restore by endpoint, not by error code. For example, a port error while turning OBS on returns false to the OBS switch, and a restart error while changing the port returns the original port number. The notification shows the string for the code of the cause, and the UI reads the enabled state of WebSocket and OBS again to see whether a service was disabled after a failed recovery.
- An unexpected exception becomes a 500, and the UI shows a notification that recommends a restart. A line other than a warning on stderr is handled the same way.
- The JSON of IPC responses does not allow `NaN` or infinity. If a value that cannot be serialized gets in, the response is replaced with the existing 500 response for serialization failures, and a response that can be read as JSON is returned.
- Error codes that have no branch in `errorHandling_Backend` (including `GENERAL_*`) and 500 become a generic notification (`common_error.unexpected_error`). The screen shows only the error code (the endpoint for a 500) and a sentence that recommends a restart and a report in Issues, and the exception text goes to the console. When you add a new error code, also add the UI branch and the `backend_errors.<code>` string in `locales/`. A notification with a branch shows this string, or the English `message` if there is no string. To see which codes have a branch, check the UI-specific handling column of [the error code list](reference/error-codes.md).
- Notifications (toasts) have a `category_id` per kind, and two of the same kind do not stack. By default they disappear after 5 seconds, and they pause while the mouse is over them.
- Error strings say "what happened" and "what to do". The English `message` is meant for logs and is not shown on screen as it is.

## Accepting and outputting messages

- A message in the message log is resent only when the primary button of the primary pointer is held for 500 ms. Releasing it, moving out of bounds, a cancelled operation, losing pointer capture or focus, or the control disappearing cancels the wait. An old timer that fires later does not send. A normal click keeps its behavior of loading the message back into the input box for editing.
- The input box, Quick Chat, conventional and real-time transcription, and OCR take the settings at the time of acceptance as one immutable snapshot. The source language, the active target slots and their languages, whether translation is on, the engine and the CTranslate2 weights, hiragana and romaji, the setting to send only the translation, the setting to show only the translation in the VR log, and the display format are used together from translation through the choice of what to read aloud. A real-time final result is fixed before it enters the queue, and the final entries of the large VR log and the captions with translations are drawn with that snapshot too. Partial captions are fixed at the moment each one arrives. Changing settings during processing does not mix up the mapping between the translation array and the slots, the OSC text, or the language information for overlays and WebSocket. The VR log does not read settings again when it draws. If translation fails late, languages or engines chosen again in the meantime are not reverted.
- The output switches for sending to VRChat, each overlay, the clipboard, WebSocket and the message log are not fixed. The current state and the delivery generation are checked right before each output. For OSC they are also checked right before the UDP send, after taking the lock that waits for changes of the send and receive targets, and a skipped send does not advance the order number. They are checked after drawing too. TTS uses the settings at acceptance and also keeps the existing cancellation by voice generation and input-source generation.
- Output to the clipboard (Voice typing mode) puts the text on the clipboard, brings the window of the app running in SteamVR to the front and sends Ctrl+V. If the window cannot be brought to the front, it only copies. The paste target is decided for each paste: the window is found by the name of the app in the SteamVR scene whose key starts with `steam.app.`. When SteamVR is not running, cannot be connected to or has no such app, it only copies. The OpenVR connection that reads the name is shared with the overlay, and if the overlay is not using it, it is closed after reading. On Linux, only X11/XWayland windows (such as VRChat running under Proton) can be paste targets. The request to bring a window to the front uses `_NET_ACTIVE_WINDOW`, and keys are sent with XTest. KDE Plasma (Wayland) shows a "Remote Control" confirmation the first time an app sends keys. The permission is per X11 connection, so the connection is reused. Nothing is pasted into Wayland-native windows.
- The subtitle overlay also checks the delivery generation, whether the output is enabled, and expiry by turning it off, after the image is turned into bytes and right before a resend. When a transfer fails, only a request that is still valid can ask the owning thread to reconnect. The wait for re-initialization is at most 5 seconds, and there is at most 1 resend. When the resend of a valid request fails or re-initialization times out, it is reported as an output exception through `/run/message_output_error` below. A request that expired through a stop, a disable or a generation update does not raise this error. The history of the large subtitles is committed only when the transfer succeeds, and expired or failed updates are rolled back. Turning it off first disables the output, then transfers and clears in order under the same lock. Shutdown of real-time recognition tidies the history, but does not show it if the large subtitles are off. The sample text also checks the enabled state after drawing.
- Right before a microphone translation is put in the speech queue, it is also checked that translation is still on and that the selected tab and the language, region and enabled state of the slot to read are the same as at acceptance. If they are not, that sentence is not read aloud, and no error is raised. Text delivery continues with the settings at acceptance.
- The microphone's original text is put in the speech queue before translation of that final utterance starts. The translation switch does not cancel reading the microphone's original text aloud.
- Inputs that can be sent to the chatbox get an increasing number, shared by all input sources, at acceptance. This covers the input box and Quick Chat, the conventional and real-time microphone, and the conventional speaker when its send setting is on. The real-time microphone gets its number when the final result is received, so the number comes before input typed while the result waits in the translation queue. The OSC comparison and send run one after another, and an older sentence is not sent if a send with a larger number has already succeeded. The other outputs and the log records continue, and the UI row is not marked failed. The skip is recorded in `process.log` without the text. The number advances only on a successful send, and no wait time or send-rate control is added. The real-time speaker and OCR do not send to OSC, as before.
- Outputs go in this order: the chatbox, the request to read translations aloud (TTS, and reading microphone translations), the VR overlay, the clipboard, the UI, WebSocket and the message log. TTS is requested without waiting for the slow drawing of the VR overlay (#556).
- If an output throws an exception, processing continues for the remaining outputs in the existing order. The exception is recorded with `errorLogging`, and a 400 notification on `/run/message_output_error` reports `MESSAGE_OUTPUT_FAILED` and the output. This is not a failure response to sending the message: the usual 200 response and notifications stay, transcription does not stop and nothing is resent automatically. The UI shows a warning per output and says that resending may duplicate content that already arrived. For the payload, see [Data formats](data-and-persistence.md#メッセージ).
- A real-time final caption waits for the delivery result before its row is finalized. Expiry, invalidation and skips caused by the chatbox order are shown apart from processing failures. However, a row whose output already succeeded is not turned back to unsent. After a stop, only `outcome` notifications for rows already shown are sent, and no new text or output is delivered ([Notifications and row states](data-and-persistence.md#リアルタイム字幕と配送結果)).

## Saving settings

### How the screens save

| Kind of control | When it is saved | Examples |
|---|---|---|
| Switches, radio buttons, selects, sliders | `/set/data/…` is sent when it is operated | Opacity, the UI language, the translation engine |
| Text fields (Settings) | On Enter, or when focus leaves the field, once the field's check accepts the value | The OSC port, API keys, URLs |
| Groups of fields (the TLS certificate and key, an address and its key, the TTS, RVC, speech server, audio route, realtime caption and message format forms) | A choice, a switch or a list edit in it at once, a slider when let go; typed text on Enter or when focus leaves the group and every field in it is accepted | The voice name, the model path |

Every setting saves by itself; there is no save button (#1111). The top bar of every settings page but About says that its changes apply at once (`DESIGN.md`).

- Escape in a text field puts the saved value back (in a group, the group's saved values).
- An API key or another credential left empty keeps the saved value; only Enter on the empty field deletes it.
- A value a field refuses is not sent. What is wrong and what kind of value would do is said under the field, which is marked invalid. A refusal by the core of a field's own save is said there too, in the words of its error code, and no notice is shown as well; the core's other reports on the same endpoint keep their notice.
- A field or group confirms a save on a success response to the request it sent. A send failure, a rejection or a response timeout does not confirm it: the edit stays and can be fixed and saved again, or put back with Escape. A failed edit does not overwrite a confirmed value. A word filter whose save failed goes back to the saved list and says so.
- A field stays usable while a save waits; an edit made meanwhile is saved once that save ends.
- No "saved" notice is shown. Leaving a page or closing Settings with a refused or unsaved value drops it, and nothing asks first.
- Selecting RVC on the RVC page is its own button; opening the page saves nothing.
- The voice, RVC, speech server and real-time speech recognition forms confirm a save on a success response to the save request they sent themselves. If whitespace in the dictionary or similar was normalized, they take the returned value and keep only the fields edited after sending. A state re-read or a response to another save request does not confirm the save. Without a response within 5 seconds, the edits are kept as unconfirmed, and a late success response to that request is still accepted. An old response that arrives after a discard or a new save does not confirm the newer edits.

- The TTS, audio route and TTS output forms send only the changed fields to `/set/data/voice_settings`. Inside the voice settings lock, the sidecar lays them over the current settings, validates the whole and then switches the route and saves. Omitted fields are kept, and the success response returns the full settings. The conditions for stopping direct voice when the route changes do not change.

### Saving in the sidecar

- Values are validated before they are saved. A value that fails validation is answered with a 400 `VALIDATION_…` and is not saved. For some values with several fields (such as language pairs), only the invalid fields are reset to their previous values, without an error.
- `config.json` is written in one batch 2 seconds after the last change. The window position, the message area ratio and hotkeys are written immediately.
- Each write exclusively creates a temporary file with a unique name in the same directory as the target. On POSIX its permissions are 0600, and it replaces the target with `os.replace` after the write and `fsync` finish. Existing temporary files and symbolic links are not used, and cleanup touches only the files that this save created. A crash partway does not corrupt `config.json`.
- Everything from reading the values to save through replacing the file happens inside one lock. A delayed save in progress does not overwrite a later successful immediate save with old values. Several sidecars that use the same storage location serialize their saves with an OS lock on `config.json.lock` (`flock` on POSIX, a byte-range lock on Windows). The lock file is not deleted. This is not a way to merge settings changes from other processes: the last complete settings saved remain.
- If reading even one value to save fails, partial settings are not saved. JSON serialization also rejects `NaN` and infinity, and on failure the last file that was saved successfully is kept. The notification and retries in this case are the same as for a write failure, and `reason` is `write_failed`.
- When a write fails (disk full, permissions, read-only and so on), the changes stay in memory, `{reason, path}` is sent on `/run/config_save_failed`, and the write is retried every 30 seconds. `reason` is one of `disk_full`, `permission_denied`, `read_only` and `write_failed`. The UI shows a persistent notification. When a rewrite succeeds, `/run/config_save_recovered` is sent, and the UI says the settings were saved. While failures continue, only the first one is notified.
- If a retry also fails, the next retry is scheduled 30 seconds later, and this continues until the save succeeds. A successful save cancels any retry that has not run yet.
- Until initialization and loading and applying the saved settings are finished, neither immediate nor delayed saves happen. If loading is interrupted, or the original file cannot be read or backed up, the original file is not replaced, and `/run/config_save_failed` reports `reason: load_failed`. In that case nothing is rewritten automatically, and saving stops until the file's content or permissions are fixed and the app restarts.
- For details, see [Data formats and storage](data-and-persistence.md).

### Changing API keys

- When the URL is changed and a key is entered for OpenAI-compatible or Custom Whisper, `{url, auth_key}` is sent once to `/set/data/openai_compatible_auth_key_and_url` or `/set/data/custom_whisper_auth_key_and_url`, even if the key is the same as the saved value. Authentication and models are checked with the entered pair, and on success both are applied. On failure neither changes. The success response also returns `{url, auth_key}`, with an empty key as `null`. If the key is empty, there is no authentication, and saving the URL and deleting the key happen together.
- Saving the pair also uses the same service's FIFO and the shared lock. An invalid URL returns the saved URL in `data` with the existing URL error, and a failed authentication or model check returns the saved key with the existing authentication error. The screen confirms the save on the response to its own request and keeps failed edits.
- For a request that changes only the URL, if the validated URL differs from the saved value and a key is saved, nothing is sent outside and nothing changes. It returns 400 with `CREDENTIAL_REENTRY_REQUIRED`, with the saved URL in `data`. For the same URL it returns 200 without network access or saving. If no key is set, only the URL is saved. Editing or deleting only the key also uses the existing endpoints.
- On screen, the key field is cleared when the URL, ignoring leading and trailing whitespace, changes from the saved value. A key the user typed is not overwritten; if none was typed, restoring the URL also restores the saved key. While the URL differs, a key is saved and the key field is empty, saving is blocked and the screen asks for the key to use with the new URL. For a server that needs no key, delete the saved key first and then change the URL. "Discard" restores both saved values, and a failed save keeps the edits.

- Translation and transcription keys are saved after authentication, the list of available models and the model to select have been checked. For translation, initializing the new client also finishes first. DeepL, which has no model list, checks authentication with the new client.
- During the check, the previous key, availability, model list, selected model and translation client are kept. Even after authentication, nothing changes if there are no models, a model cannot be selected or the client cannot be initialized. The existing `AUTH_…` or `TRANSCRIPTION_API_AUTH_FAILED` is returned, with the saved key in `data`.
- Changing or deleting a key, choosing a model and changing the OpenAI-compatible or Custom Whisper URL for the same service are processed in the order received. A delayed authentication check does not overwrite a later model choice with the old one. A translation client whose selected model changed during the check is not applied either, and the saved key is returned in the error's `data`.
- Queries to the service run outside the shared lock. When all checks are done, only the target key is updated inside the shared lock, and the prepared client and settings are applied. Deleting a key uses the same lock. A simultaneous change to another service's key is not overwritten. The file is saved on the same schedule as ordinary settings.
- Changing only the OpenAI-compatible URL follows the key re-entry rule above. An invalid URL returns `CONNECTION_OPENAI_COMPATIBLE_URL_INVALID`, with the saved URL in `data`. The key, availability, model list, selected model and running client do not change.
- If related settings change while an OpenAI-compatible key, or a URL and key pair, is being checked, the client for the old combination is not applied, and an authentication error is returned.
- The same rule applies to changing only the Custom Whisper URL. An invalid URL returns `CONNECTION_TRANSCRIPTION_CUSTOM_URL_INVALID`, with the saved URL in `data`. The key, availability, model list and selected model do not change.

## Consent and sending data out

- A model is downloaded only after the screen shows its name, provider, exact size and license, and the user checks the box and starts the download. The catalog pins the version, size, SHA-256 and license (`native/ops/src/downloads/catalog.rs`). Local translation (ONNX Runtime) models, once published, are also downloaded from the catalog target `translation` through the same confirmation (the download of the fixed CTranslate2 weights of 0.4 and earlier was retired in 0.5.0). There are no implicit downloads from other repositories or the Hub cache.
- A model already on your PC is used from its card, with no review or consent in between (#1263): nothing is acquired, and the consent and any confirmation were given when it was downloaded. `/run/check_model_download` (`{id, catalog_version}`) checks the size and SHA-256 of its files and never uses the network. Files that do not match are left as they are, the job fails with `model_files_changed`, and the card offers the download's review, which asks for the consent before they are downloaded again. A model that is not on the PC is refused with 409 `model_not_downloaded`. Once the check is ready, the card applies the model, as a download's "Apply" does; a caller that goes on once the model is there (the speech recognition fix, #1232) applies it itself.
- A model downloaded from a catalog in Settings is applied once its download is ready, as the first-run setup applies its models (#1308 ★3, decided on 2026-11-28). A model whose server or feature runs stays ready, with its "Apply model path" and the reason. Speech recognition models are chosen for each input instead, under "Mic input's model" and "Listening's model" in the speech.cpp part (#1308 ★1): each is chosen among the recognition models on the PC, checked as above, and applied for its input alone. Their cards download them and say which input uses each ("In use (Mic input)", "In use (Listening)"). A recognition model on the PC that an input does not use yet also offers "Use this model" on its card, and its card is pressed anywhere for it: it opens a small menu of "Use for Mic input" and "Use for Listening", where an input that uses the model already says so and cannot be chosen. An item checks the model and applies it for that input alone, with the same check and apply as the fields. While a recognition server runs (Mic input's or Listening's own) or the paths have unsaved edits, the menu says why and its items wait. A card that both inputs use has nothing to press. The fields stay. A downloaded recognition model is applied by itself only while Mic input has none, as Mic input's model. When a recognition model comes to be set and no speech recognition engine is selected, speech.cpp is selected.
- Models with a non-commercial license (such as NLLB-200) ask, separately from consent, for confirmation that use is limited to non-commercial purposes (#411). The catalog row's `restrictions` follows from the license string, and a Creative Commons NonCommercial license gives `["non_commercial"]`. Translation models whose license includes the Gemma Terms of Use (TranslateGemma) have `gemma_terms` (ADR-015). The TTS model Irodori-TTS v4 Large is also under the Gemma Terms of Use but gets no such confirmation (on 2026-11-19 it was decided to limit it to translation models). The confirmation screen shows the license name and what the restriction is, with a checkbox per kind under the consent. For `gemma_terms`, it says that the Gemma terms of use and the prohibited use policy also apply to the people who use the model. The `/run/start_model_download` request adds `acknowledged`, with the kinds that were confirmed, to `{id, consent, catalog_version}`. If it is missing, the request is refused with 400 `model_download_restriction_unacknowledged`; an unknown kind, a duplicate or a kind the model does not have is refused with 400 `download_request_invalid`. No file is written and nothing is sent over the network. Requests for models without restrictions do not change. The confirmation is recorded neither in `receipt.json` nor in the settings ([Model downloads](../voice-stack/model-downloads.md#非商用のライセンスの確認)).
- The card of a local translation model shows the memory used during translation (`guidance.reference_memory_bytes`). A model that has not been measured shows "Not measured yet", and no number is made up. If the device used for translation (`SELECTED_TRANSLATION_COMPUTE_DEVICE`) is the CPU, the figure is compared with the total RAM; if it is a GPU, with that GPU's total memory. The comparison with RAM uses the amount left after the OS and VRChat (13 GiB), and the comparison with a GPU uses the amount left after VRChat (4 GiB) (the same goes for TTS and speech recognition models). If it does not fit, the card and the download confirmation say that performance may fall short. It is only guidance, so it blocks neither choosing nor downloading (#405, #597, [Model downloads](../voice-stack/model-downloads.md#性能不足の可能性の警告405)).
- When the path of a downloaded model is applied, the re-verification accepts a cancel of the same model and job even while the Apply response is pending. The Apply and cancel responses are awaited separately, and one response does not release the other's wait. While waiting, no other apply or download can start. If there is no response for 10 seconds, a warning is shown and every wait, including Apply, is released (#563). Even if a response is lost, the other operations do not stay blocked until the app is restarted. When the wait is released, the job may still be verifying (`verifying`, `cancelling`). A download or another apply sent during that time is refused by the core with `download_busy` (another model is downloading), so it does not overlap the verification. A cancel of that job is accepted.
- Translation models are downloaded with the same catalog confirmation and consent as other models ([Model downloads](../voice-stack/model-downloads.md)). A saved selection, consent to the NLLB terms given when selecting it, or the startup download switch does not by itself count as consent to download. NLLB always shows its non-commercial restriction and is never the default. The download request for the built-in model (CTranslate2) of 0.4 and earlier, and its consent (`consent: true` and `manifest_version`), were removed from the core in 0.5.0 and from the screens in #1015.
- Models are not downloaded automatically at startup. Automatic download at startup (`AUTO_DOWNLOAD_MODELS`) was retired in 0.5.0 together with the old CTranslate2 weights ([Core integration](../voice-stack/core-integration.md)). The settings key and endpoints such as `/get/data/auto_download_models` remain for compatibility, but the core does not read the value, and Settings shows no switch for it. Downloads happen only as explicit downloads that the user consented to in Settings or on a confirmation screen ([Model downloads](../voice-stack/model-downloads.md)).
- For the tokenizer used to turn translation on, to run inference and to decide whether a model is downloaded, only the pinned files whose size and SHA-256 were verified are copied to a dedicated temporary folder and read with `local_files_only=True`. If a file is missing or fails the check, `TRANSLATION_MODEL_MISSING` is returned. If the files pass the check but the tokenizer cannot be built (Transformers cannot be loaded, or loading failed partway), `TRANSLATION_MODEL_LOAD_FAILED` is returned and a notification reports it. If a failure that downloading again cannot fix were reported as `TRANSLATION_MODEL_MISSING`, each consent on the confirmation screen would lead back to the same screen. When `TRANSLATION_MODEL_MISSING` comes back as the result of pressing the translation switch, the UI opens the download confirmation screen (provider, license, size, consent) on the spot. When the user consents and the download finishes, the UI turns translation on again. The confirmation screen says so. If the download is cancelled or fails, or the screen was opened from "Review download" in the conversation area, translation is not turned on. When the code comes back from a request other than the switch, a notification reports it. Having no model yet is normal on the first launch, so `TRANSLATION_MODEL_MISSING` is neither kept in `error.log` nor counted in the usage data `error` (`"reported": False` in `ERROR_METADATA`). `TRANSLATION_MODEL_LOAD_FAILED` is kept in both. The pinned version is downloaded from the network only by an explicit download with consent and by a startup download with recorded consent.
- For CTranslate2 inference, the weights at the time the message was accepted are compared with the loaded weights. If they differ, the weights at acceptance are loaded locally with the same storage location, device and compute type as the previous load. Switching weights and inference are protected by the same lock, so models, tokenizers and language codes are not mixed. Messages accepted before the switch are processed with the original weights.
- If verifying the CTranslate2 weights or tokenizer, or deciding the compute type, fails, the usable original model is kept. Once preparation is done, the original model is released before the next one is allocated, and if the allocation fails, the state becomes not loaded. If CTranslate2 or Transformers is unavailable, turning translation on does not succeed: the existing load error is returned and translation stays off.
- Existing built-in models are also used only after the size and SHA-256 of every pinned file are verified. The verification record is tied to the manifest and to changes in the files, and old records that only say a load succeeded are not used. User files are not deleted because of a conflict or mismatch between old and new names. This uses an OS lease on the root, a dedicated staging area, a size limit during transfer, a deadline per file, cancel and join at shutdown, and completion notices with identifiers. At shutdown, delivery from every input source is invalidated, cancellation is signaled to both the catalog download and Apply and the built-in model download, and then a wait with a deadline follows. For details, see [The model download contract](../voice-stack/model-downloads.md#内蔵モデルの検証保存終了).
- Cloud translation and speech recognition engines are used only when the user chooses the engine. Services that need a key also need the key registered. Choosing the engine counts as consent to sending data to that service. Google's web speech recognition, which worked without a key, was removed because it used an unofficial endpoint and a generic key.
- Translation with an LLM sends the chosen service the prompt and the recent conversation history as well as the current text. With the bundled settings, this includes up to 5 entries from chat, the microphone and the speaker. No information about the runtime environment is sent apart from the `User-Agent`. For what is sent and the history limits, see [Translation with an LLM](external-interfaces.md#llmでの翻訳).
- Changing the translation engine, endpoint or model invalidates the translation history so far. Switching back to the original destination does not restore it. Conversation while translation was off, and conversation accepted before the change but processed after it, does not enter the new history. The message log on screen and saved logs are not deleted.
- In new settings, no speech recognition engine is selected. Turning on classic transcription with no engine selected does not open recording and returns 400 `TRANSCRIPTION_ENGINE_NOT_SELECTED`. The UI opens a screen to choose Local (speech.cpp), or to open the engine settings and choose a cloud engine. Choosing Local (speech.cpp) confirms the save response for the choice and then continues the user's original turn-on action. When the engine settings are opened, a cancel or a failed save does not start anything. If the recognition model or the VAD model for Local (speech.cpp) is not set, that turn-on action reports it through the real-time path described below, with `TRANSCRIPTION_SEND_NOT_READY`/`TRANSCRIPTION_RECEIVE_NOT_READY` (`details.reason` is `realtime_asr_model_missing` or `realtime_vad_model_missing`). Models are downloaded only after their review and consent, in Settings → "Speech recognition (ASR)" or from the switch's fix below. This screen does not download them.
- There is no automatic switch from the selected speech recognition engine to another one. If the API recognizer cannot be built, `TRANSCRIPTION_ENGINE_UNAVAILABLE` points the user to the engine settings. The recognizer is initialized before the recording device is opened. A saved Google selection is reset to no selection when it is loaded ([Storage format](data-and-persistence.md#音声認識エンジンの選択)).
- On Linux, the main Mic input and Listening switches use the local speech.cpp real-time path, independent of the choice above. They skip this selection screen and need the existing readiness check and the user's turn-on action. On Windows, the switches use this path only when Local (speech.cpp, `SpeechCpp`) is chosen as the speech recognition engine (the server is the bundled or external one from the real-time speech recognition settings), and use conventional recording with a cloud engine. When changing the engine changes the path, switches that were running on the previous path are turned off. When the engine changes while staying on conventional recording, transcription switches that were running are turned off as well. Nothing more is sent to the previous engine. Turning a switch on again starts it with the new path or engine.
- When a main Mic input or Listening switch is refused because speech recognition misses something, the main window offers the fix where the switch is, instead of a notice that names a settings page (#1225, decided on 2026-11-26). For `realtime_asr_model_missing` and `realtime_vad_model_missing` it leads to the first-run setup, which shows the models it downloads and their size and downloads them only after consent. For `realtime_language_auto_unsupported` and `realtime_language_unsupported`, the refusal also carries `details.languages`, the languages the model takes. One of them can be chosen there; it is saved as the source's language, and once the saved settings come back with it the switch is turned on again. When the model cannot tell the language and the server is the bundled one, a model that can is also offered through the download catalog's review (size, license, consent): the one the catalog marks as telling the language (`detects`) and recommends for the most languages, Qwen3-ASR 0.6B today. Once it is downloaded it is applied to the refused source alone and the switch is turned on (#1242): as Mic input's model for Mic input, and as Listening's own model (`listening_model`, `"source": "speaker"`) for Listening, which leaves Mic input's model as it was. For `realtime_asr_models_do_not_fit` (Listening's own model does not fit beside Mic input's, decided on 2026-11-27), it offers one model for both: Listening's own model is taken away, and once the saved settings come back without it Listening is turned on again. An apply refused while the ASR server or captions run (`model_target_busy`) is reported, and nothing is turned on. When the bundled server did not start or stopped (the `speech_server_*` reasons, #1308 N-14), the dialog says why in the switch's words: a server that was busy, slow or gone (`speech_server_busy`, `speech_server_start_timeout`, `speech_server_exited`, `speech_server_not_ready`) is offered "Turn on again", and one whose model, device or driver failed opens the server's settings as its main action; a server a switch may not start (`speech_server_autostart_off`) opens "ASR server". Each case can also open the exact setting. A bundled speech.cpp that is missing or fails its check (`speech_bundle_missing_or_invalid`, kept through the switch's start, #1314) is not fixed in the settings: the dialog says so and opens the user guide's steps to install the app again. Other reasons keep their notice. A greyed-out switch whose recognition models are missing opens the same setup from its feature button.
- The local Whisper (faster-whisper) engine was removed in #288. If the saved `SELECTED_TRANSCRIPTION_ENGINE` is `"Whisper"`, it is moved to Local (speech.cpp) once when loaded, and a notice that says it was moved and which models are needed is shown once ([Storage format](data-and-persistence.md#ローカル音声認識の移行)). Neither the notice nor the migration downloads models. Whisper weights that earlier versions downloaded are no longer read, and they are deleted only when the user reviews them in Settings and chooses to delete them.
- A change to the screens must not by itself turn on a microphone, download models, send messages or change audio routes ([Contracts](contracts.md)).
- Usage data (telemetry) is on by default. Only 2 kinds of events are sent, `app_started` (once a day) and `error` (once a day per error code), with the send time (ISO 8601, UTC), the app version, the OS type and version, the display language and the PC configuration (CPU name and logical core count, memory size rounded to a step, GPU name, type, video memory size and driver version). "A day" is counted by the UTC date. Conversation text and audio, the names of audio devices, users and the PC, paths, and numbers that identify the PC are not sent. What is sent is passed to the UI through `/get/data/telemetry_preview` and shown to the user on the notice screen and in Settings. This response is built by the same function as the send (`build_event`), so only the time differs from what is sent. The last 20 sent events are kept in `telemetry_state.json` and shown in Settings. The codes in `error` are only those in `ErrorCode` and in the list of voice-related failures (`errors.REPORTED_FAILURES`). Failures not in the list are grouped into the per-feature `…_failed_other` or are not sent. Codes in `ErrorCode` that answer an expected state rather than a failure are marked `"reported": False` in `ERROR_METADATA` and are not sent (currently only `TRANSLATION_MODEL_MISSING`). Until the user answers on the notice screen (until `TELEMETRY_NOTICE` reaches the current version of the notice), nothing is sent even if the setting is on. `ENABLE_TELEMETRY: false` in a settings file from an earlier version is a value nobody chose, so it is decided again by the answer to the notice. Only the answer to the notice (`/set/data/telemetry_notice`) can start sending (security audit SEC-07). `/set/enable/telemetry` only changes the setting's value: it does not count as answering the notice, and nothing is sent while the notice is unanswered. While the notice is unanswered, the switch in Settings is shown off whatever the setting's value is, because nothing is being sent in that state. A note below the switch says that no choice has been made yet and that nothing is sent now. Pressing the switch at that point sends the answer to the notice (send), because Settings shows the same content to be sent as the notice. `/set/disable/telemetry` also counts as an answer (do not send). Neither is relayed from the VR UI ([Relaying from the VR UI](external-interfaces.md#tauriのコマンド)). "Decide later" and Escape on the notice are not answers: they only close the screen for that run, nothing is sent, and the notice appears again on the next start. With the environment variable `VRCT_TELEMETRY=off`, nothing is sent whatever the setting is, and the notice is not shown. Tests that launch the real app launch it with this variable. Send failures are ignored and not retried. The upstream project's Aptabase key and SDK are not used ([External connections](external-interfaces.md#利用状況の通知)).
- App updates use the Tauri updater ([App updates](external-interfaces.md#アプリの更新)). The check at startup is controlled by `CHECK_SOFTWARE_UPDATES` (on by default) and runs once, after the backend finishes initializing. When the user changes the update channel, the check runs again on the new channel ([App updates](external-interfaces.md#アプリの更新), #466, #1017). Only the query for the latest version and the download request are sent; conversations, audio and settings are not. Copies installed from deb or rpm and development builds are not checked. If checking or applying fails, the app stays usable, and a failed apply keeps the current version and shows the reason. The old Python update process (`BUILTIN_UPDATER_ENABLED = False`) is not used. The backend's update endpoints use the same updater, and the startup check (`/run/software_update_info`) makes no network access when `CHECK_SOFTWARE_UPDATES` is off. The "Update available — update now" button on the error screen appears only when a newer version exists and the copy can be replaced from inside the app (`mode` is `install`).

## Secrets

- API keys are not written to `config.json`; they are stored in the OS credential store (Credential Manager on Windows, Secret Service on Linux). Keys that 0.5.x saved in `secrets.json` are moved once they have been written to the OS store and read back. If the store is unavailable, keys are not silently lost, and they are not written to a plain-text file instead. The app does not show a dialog to unlock the keyring ([Where API keys are stored](data-and-persistence.md#apiキーの保存先), [ADR-013](../adr/adr-013-secret-store.md)). The WebSocket token is still stored in plain text in `config.json`. The permissions of `config.json` are 0600. If the saved WebSocket token is invalid, it is repaired with a new secret value, and the server is never started with an empty token ([Network settings](data-and-persistence.md#ネットワーク設定)).
- In logs, the values of fields whose names contain `auth_key`, `api_key`, `password`, `token`, `secret`, `voice_settings` or `instructions` become `***MASKED***`. The core adds `client_id`, `user_model`, `translation_catalog`, `transcription_catalog`, `vocabulary` and `speaker_names` to these (`SENSITIVE_ENDPOINT_MARKERS` in `native/core/src/log.rs`). `vocabulary` is the term dictionary in the real-time speech recognition settings, and it is masked because it contains names of people and places (#446). `speaker_names` are the names the user gives to the voices told apart by speaker diarization (#447). The core also masks nested fields inside requests, judging by the field name as it does for responses. Conversation text is not written to diagnostic logs. The user's home folder in a path contains the OS user name, so it is written as `~`.
- Before a URL is logged, the user information and all query values are removed. Provider failures are recorded with `errorLogging(provider=..., status=...)`, which keeps only the service name, the exception class, the HTTP status if one was received, and the file name, line and function name where it happened. The exception message, the chain of exceptions that caused it and source lines are not recorded. Exceptions from SDKs, and exceptions marked at the provider call boundary, are handled the same way when they reach the shared handling higher up.
- General `errorLogging()`, for file operations, settings and the like, keeps a traceback that includes the exception message and the chain. However, strings that match a saved API key, authentication token or WebSocket token, Bearer tokens, authentication headers and query or JSON values that contain keys are replaced with `***MASKED***`. The same processing applies when the log cannot be written to the file and goes to standard output. An IPC error built from an exception includes the message with the same masking for a general exception, and returns only the class name for a provider exception.
- The core does not use LangChain or LangSmith and calls each API directly. Conversations are not sent to LangSmith, including with local LLMs (the Python backend of 0.4 and earlier removed the `LANGSMITH_*` and `LANGCHAIN_*` environment settings and disabled tracing).
- Requests from the VR UI do not pass through API keys, tokens, model downloads, actions that open files, quitting or updating (`src-ui/logics/common/vrPanelWire.ts`).
- API key fields in Settings hide a saved key behind an "Edit" cover and turn off spell checking and autocomplete.

## Internationalization

- All UI text lives in `locales/`. `en.yml` and `ja.yml` must always be updated. The UI languages are English and Japanese only. Korean and Chinese could be chosen as UI languages up to 0.1.0 and were removed in 0.2.0, because many strings were untranslated and more and more places showed English. If saved settings chose one of them, the app starts in English. Korean and Chinese can still be used as languages to translate.
- The page language (`<html lang>`) follows the UI language.
- Changing the UI language does not rebuild the screen. The open settings page, expanded folds, half-typed text and focus stay, and only the text changes to the new language. The same holds when the language is changed from the VR UI's settings (#904).
- The sidecar's `message` is a default English sentence. The screen shows the string looked up from the error code.
- Only the language and country pairs in the core's language table (`native/core/data/transcription_languages.json`) are accepted.

Showing and searching language names and country or region names:

- Display names and accessible names on the main screen, in Settings and in the VR UI come from `Intl.DisplayNames` with the current i18next UI language. Language tags are split into language, script and region with `Intl.Locale`. The script is kept so that Simplified and Traditional Chinese are told apart. Switching the UI language also updates the display.
- The source of truth for the tags is the `Google` column of `native/core/data/transcription_languages.json`. `python tools/language_codes.py --write` generates `src-ui/logics/common/languageCodes.ts` for the UI, and the tooling check detects differences. This table is also used for saved languages that dropped out of the choices because of the model selection, and for old OCR settings. The real-time ASR and UI language choices use the language tags they already have.
- If there is no tag, the tag is invalid or the platform cannot return a display name, the original English name is used. The fallbacks for language and region are independent.
- The language lists on the main screen and in VR are sorted by display name with `Intl.Collator`. Search covers language and region names in the UI language and in English, and ignores case and full-width versus half-width. Enter picks the first candidate shown, but not while the IME is committing a conversion. In VR, nothing changes if the first candidate is already selected or unavailable.
- The VR language list keeps 2 columns, and when there are 50 or more candidates before a search, it draws only the rows near the visible area. The selected candidate is shown when the list opens, and a search goes back to the top. Candidates off screen can still be reached with the initial-letter buttons or Tab, and candidates that are busy or unavailable still cannot be chosen, as before. Sorting happens only when the candidates or the UI language change, and a search filters that sorted result.
- VR's "Choose from all languages" has buttons that scroll to the first candidate for an initial letter of the language names shown. Japanese uses the ア, カ, サ, タ, ナ, ハ, マ, ヤ, ラ and ワ rows plus "Other" (kanji and other scripts), English uses A to Z and Korean uses the Hangul initial consonants; only groups that have candidates are shown. In Japanese, voiced and semi-voiced kana, small kana, hiragana and half-width katakana are put in their base row, and a leading long-vowel mark is skipped. ン goes in the ワ row. English and Korean also have "Other" for names that cannot be classified. Chinese (Traditional and Simplified) and unsupported UI languages get no jump buttons: readings and stroke counts are not guessed, and the list and search are used instead. The buttons do not change the sort order or the selected value, and they follow filtering and UI language changes. They are not added to the desktop language list.
- Settings search also matches the language names for OCR, the UI language and downloaded real-time ASR models, in the UI language and in English. Each UI language choice also shows that language's own name for itself.
- The English identifiers in storage, IPC, OSC and presets do not change ([Data formats and storage](data-and-persistence.md#言語の組タブごと)).

## Stop and mute

- "Stop speech" (`/run/stop_voice`) stops only TTS. It empties the queue and also stops speech in progress. It does not change whether TTS is on or off, or the mute state.
- "Mute" (`/run/mute_voice`) stops the audio route. On the managed route (the Linux virtual microphone), it stops both TTS and RVC's converted audio. On Windows it replaces both with silence just before the output device; there is no block at the OS level, so the audio stream itself does not stop. The setting that suppresses direct voice during microphone TTS also silences the converted audio this way on Windows. The speaker monitors for TTS and for converted audio are silenced too, and audio waiting to play on a monitor is dropped. Starting conversion while muted does not make the monitor sound. The mute state is saved in `voice_mute_state.json` and lasts across restarts.
- When "Speak through voice conversion" (`VoiceSettings.conversion`) is on, TTS is sent to the conversion input instead of the output device while voice conversion is running. During speech, TTS is converted in place of the microphone, and the microphone comes back when it ends ([ADR-007](../adr/adr-007-translated-speech-through-voice-conversion.md)). Mute also stops converted TTS. In this mode, the setting that suppresses direct voice during microphone TTS silences only the blocks that come from the microphone and lets the converted TTS out. On Linux, this suppression is done by the conversion process and is not confirmed by the OS gate. The setting cannot be used together with "Mix direct input and speech". When voice conversion is not running, TTS goes to the output device as before.
- Muting and unmuting do not change the conversion worker or whether TTS and RVC are on. The monitor also stays muted until the existing resume confirmation is done, and only new converted audio captured after unmuting goes to the monitor. If notifying the worker of the mute fails, it is reported with the existing `vc_router_failed` or `vc_router_timeout`, and the shutdown on failure closes the monitor.
- On the external route on Linux, only TTS is stopped. The converted audio and routes of external apps are not controlled. On Linux, in-app converted audio and its monitor can start only on the managed route, so the external route has no exception for the converted-audio monitor. On Windows, in-app converted audio flows to the output device and is muted as described above.
- Stop speech and mute also stop previews in the model catalog ([UC-19](use-cases.md#uc-19-読み上げの声を試聴する), [UC-20](use-cases.md#uc-20-ボイスチェンジャーの声を試聴する)). A preview does not start while muted.
- TTS and RVC have separate switches, and operating one does not stop the other.
- `VOICE_SETTINGS.mic_mode` chooses how final utterances from real-time microphone recognition are read aloud. The values are `off` (not read), `original` (the original text is read in the spoken language) and `translated` (the translation is read when translation is on and the translation for the chosen slot succeeded). `original` and `translated` use the same output, audio route and direct voice setting (`direct_policy`).
- The feature switches on the main screen ignore key repeat from Enter and Space. Even after the stop response arrives, the same key held down does not turn the switch on again. To cancel a pending TTS or RVC start, press a key again or click.
- Stop requests skip the queue and are processed at once ([IPC protocol](ipc-protocol.md#並行性とロック)).
- Stopping advances the generation number. Messages queued before the stop are still sent and recorded, but audio from the old generation is not played.
- A final result of real-time recognition gets the voice generation number before it enters the session's receive queue, and keeps it while waiting for the caption notification and translation. Even across a stop speech, a voice mute and resume, or TTS off and on, a waiting result is not read aloud as audio of the new generation. Text delivery continues.
- When VRC mic mute sync is on, and a VRChat mute is received or a recheck of the state starts, the delivery generation of microphone results advances. Results waiting for translation, drawing or the queue are not delivered even after unmuting. Classic transcription also keeps the delivery generation from the start of inference for the whole batch of results, and drops the remaining results if it expires partway. Captions and final results received while muted are dropped too. Results from the speaker, OCR, the input box and Quick Chat are not affected.
- When the user turns off microphone or speaker transcription or OCR, or an error disables the feature, the delivery generation of that input source advances before the wait for cleanup. At shutdown, delivery from every input source is invalidated before waiting for cleanup, and acceptance of new messages is closed too. After that, advancing the generation does not reopen acceptance. The response to shutdown and the required completion notifications stay. The generation is checked right before each output, and results that come back late are not newly delivered to OSC, overlays, WebSocket and OBS, the message log, UI and VR rows and captions, the clipboard or TTS. Resuming does not bring old results back. Unpublished history from expired drawing is discarded too, so that it does not mix into later displays. Content already delivered is not withdrawn, and the cleanup wait limit and the shutdown guards stay.
- Refreshing the device list, pausing for Settings and switching from classic transcription to real-time recognition do not advance the delivery generation. Classic transcription results already accepted continue to be delivered. Settings passes `{"reason":"settings_pause"}` to the transcription disable endpoint to tell it apart from the user turning it off. When Settings closes and the previous state comes back, it passes `{"reason":"settings_resume"}` to the enable endpoint. If the user stopped the built-in speech recognition server during the pause, resuming an input that uses that server is refused: `200` with false is returned, and the switch stays off. Closing Settings alone does not start a stopped server again. When the user presses the switch on the main screen, the request arrives without a reason, so it is not refused. A lost device does not invalidate delivery when switching to a fallback device either; it invalidates delivery when there is no fallback and transcription is disabled. The existing session generation and freshness limits of real-time recognition still apply.

## Initialization, offline use and missing capabilities

- Until initialization finishes, turning translation or speech recognition on or off and sending messages are held back with 423. The UI shows the main screen right after launch, but keeps it `inert` until `IsBackendReady` is true, and tells assistive technology that it is starting through `aria-busy` and a live region off screen. Values not yet received from the sidecar are shown as placeholders of the same size (skeletons), which are replaced with the real values without layout changes once everything is ready. The placeholder animation is subtle, and it stops under `prefers-reduced-motion`. Settings, consent dialogs and saving the window position and size start only once everything is ready.
- The main window is created hidden. The app reads the saved position and size from `config.json`, applies them to the window and then shows it (`src-tauri/src/window_placement.rs`). The window is not moved after it is shown. When nothing is saved (the initial values), it is placed in the middle of the work area of the monitor the window is on. Its size is 870×654 CSS pixels. When the saved position is on no monitor, the window is fitted inside the monitor it is on.
- If some initialization items cannot be read or applied, the rest are applied and the screen opens with a warning. If the sidecar itself fails to start, a failure dialog appears over the inoperable main screen and shows the reason (it could not start, or it exited while getting ready), what to do next and buttons for a manual retry and quitting. Default values, the session owner and the retry conditions follow [Startup and initialization](ipc-protocol.md#起動と初期化).
- `/run/enable_ai_models` is false when a built-in model that the currently selected engine needs is missing. The UI shows no notification in this case. This applies only when the translation engine of the selected tab is CTranslate2 and the translation model is missing (`Controller._missingBuiltInModelInUse`). A missing model for an engine that is not selected does not make it false. Text chat and external voice engines remain usable.
- While the conversation is empty, the conversation area shows what is missing, together with a way to set it up (judged from the model list the UI holds and the speech server settings, `src-ui/logics/main/setupNeeds.ts`). If the translation engine is CTranslate2 and the translation model is missing, it shows a button that opens the download confirmation when the model can be downloaded (when the download catalog has an entry for the selected model), and otherwise a button that opens the list of translation engines. If the speech recognition engine is Local (speech.cpp), the real-time speech recognition server is the bundled one, and the speech server's `asr` profile has no recognition model or VAD model, it shows a button that opens Settings → "Speech recognition (ASR)". Nothing is downloaded from here.
- If the translation model is missing when the translation switch is pressed (`TRANSLATION_MODEL_MISSING`), the download confirmation opens on the spot instead of a notification (`src-ui/views/app/_app_controllers/TranslationSetupController.tsx`). If one of the catalog's translation models of the selected model's kind is downloaded there, the app applies it once verification finishes, and turns translation on once the core reports the model as downloaded (#1015). Applying a translation model does not write settings. Translation is not turned on if the download fails or is cancelled, if another model listed on the confirmation screen is downloaded, or if the screen was opened from the entry in the conversation area. The model selection and whether the microphone is on do not change.
- The feature switches on the main screen are disabled while a prerequisite is missing (`src-ui/logics/main/switchBlocks.ts`). On mouse hover and on keyboard focus, a tooltip shows the reason and where to set it up. Screen readers read the same sentence as the switch's description. The prerequisites come from the checks above and from state that the settings already hold. A switch is disabled when: for Translation, the CTranslate2 model is missing (including while it downloads); for Mic input and Listening, the local speech recognition model is missing; for Chat reading, the chosen language is not supported or its model is missing (`/get/data/ocr_model_readiness`, described below); for Text to speech, both kinds of content to read are off, no output device is chosen on a route other than the managed one, or no voice has its model; it names every one of these that is missing at once, in the TTS page's order, and its icon leads to the first (#1314); for Voice changer, the saved model and runtime are missing or the audio route is not ready. `/get/data/ocr_model_readiness` only checks whether the files exist and does not look for windows. It is included in the startup settings and also covers whether the chatbox detector model exists and whether the settings use it, and the Chat reading page in Settings uses it to draw the model list and the detector field before the answer to its own query arrives. A state that has not arrived yet does not disable a switch. Once the prerequisites are met, the switch becomes active again without a restart.
- Pressing a switch greyed out for a missing prerequisite opens a dialog that says why it cannot be turned on yet, with Close and the step the icon button below takes (#1314; the speech recognition switches' dialog has the same shape, #1225). It turns nothing on. A switch that cannot be used for another reason (the engine is gone, a change on its way) does nothing. Unless the display is the narrow icon-only one, the icon on the left of each feature is a button, placed as an element separate from the switch. The icon button opens the place to set things up when a prerequisite is missing, and the feature's settings when nothing is missing. For Translation it opens the download confirmation when the selected model can be downloaded, and otherwise the list of translation engines. Mic input and Listening open "Speech recognition (ASR)", and the others open the settings page of the same name. The button's name and tooltip say where it goes. When the result of the prerequisite check arrives, the layout and size of the row do not change, and no button is added under the switch. Nothing is downloaded or turned on from here. A switch that is on, or is being turned on, is not disabled when a prerequisite disappears, so that it can still be turned off. A missing prerequisite is reported through the switch's error and guidance, as before. Operations from hotkeys do not go through this check.
- The check runs once, on the main screen, and the result goes into the `SwitchBlocks` atom (`SwitchBlocksController`). It contains only a reason and a destination identifier per switch, and no user data. Both the main screen's switches and the VR UI launcher read this atom. The rule that leaves out switches that are on or switching is shared too (`activeSwitchBlock`).
- The 5 switches of the VR UI launcher (Translation, Mic input, Listening, Chat reading, Text to speech) are disabled under the same conditions. The text-to-speech switch and the stop beside it press the main screen's own switch and the top bar's stop (`vr-panel-voice`, #1314); the stop is never disabled. The buttons are grayed out with a warning mark, and pressing them does nothing. The reason, and where in the PC's settings to set it up, appear in the button's tooltip. VR has no other place to read the reason, so this tooltip appears even when operation tooltips are turned off. VR does not open settings pages. The lock while the settings page is open (in a browser; the settings window locks nothing, #1236) is shown before a missing prerequisite. Once the prerequisites are met, the buttons become active again without a restart.
- At startup, only the engines in use are checked (#457). For translation, these are the engines selected in any tab and the engines that can be checked without going outside (CTranslate2, and LM Studio, Ollama and OpenAI-compatible at a loopback address); for speech recognition, the selected engine and Custom Whisper at a loopback address. Loopback means `localhost`, `127.0.0.0/8` and `::1`. The checks run in parallel, one thread per engine (`native/core/src/controller/translation.rs`, `transcription.rs`). Other engines are not contacted at startup. If a key is saved (plus the URL for OpenAI-compatible and Custom Whisper, and the Client ID for Papago), the engine is left selectable and is checked when it is chosen (`/set/data/selected_translation_engines` for translation, `/set/data/selected_transcription_engine` for speech recognition) or when it is first used for translation. The model list is fetched at that time. A cloud engine that is already unusable is not checked again when it is chosen. LM Studio and Ollama on the LAN have no key and cannot be used without a model list, so unless they are selected, they stay unusable until the connection check in Settings is pressed.
- CTranslate2 is the name of the local translation engine that remains in the settings. What runs is M2M100 and NLLB-200 on ONNX Runtime (`native/translate-onnx`), and the default model is selected by the name `m2m100_418M-ct2-int8`.
- API keys are checked at startup and when an engine is chosen, and an engine that could not be checked is marked unusable. The key is not deleted, because a check can fail when offline, on a timeout, on 429 or on 5xx as well as when the key is rejected. Tabs that had selected an engine that became unusable are set back to CTranslate2, and the new selection and list are sent to the UI with `/run/selected_translation_engines` and `/run/translation_engines`. The failed check itself is not notified. For speech recognition engines, the selection does not change; the engine's model list, the selected model and the Deepgram language are cleared (`forget_failed_engine` in `native/core/src/controller/lifecycle.rs`, [Consent and sending data out](#consent-and-sending-data-out)).
- The engine checks at startup have no per-stage deadline. The translation checks, and then the speech recognition checks, each wait until all their threads finish. How long one check takes is set by the network timeouts below. Startup as a whole has a 180-second deadline (`STARTUP_LIMIT` in `native/core/src/backend.rs`). When it passes, the core logs it and exits with code 124, stops what it started after the checks and does not open the endpoints. The Python backend of 0.4 and earlier cut off each check stage at 30 seconds (`_runEngineChecks` in [`controller.py`](https://github.com/kein5/astarot/blob/v0.5.2/src-python/controller.py)).
- Key checks and model list requests use a timeout of 3 seconds each for connect, read and write, and are not retried (`DISCOVERY` in `native/translation/src/providers/mod.rs` for translation, `DISCOVERY` in `native/transcription/src/providers.rs` for speech recognition). The check whether LM Studio and Ollama are running waits 0.2 seconds (`LOCAL_PROBE`), and the Ollama model list (`/api/tags`) waits 2 seconds (`OLLAMA_TAGS`). The Gemini model list is cut off at 8 seconds in total, including paging (`DISCOVERY_DEADLINE`). Each page's timeout is shortened to the time left, and no further page is fetched after the deadline. The other checks have no overall deadline, and OpenRouter (`/auth/key` and `/models`) and Deepgram (key and models), which send 2 requests, wait up to 3 seconds for each. Checks at startup and from Settings use the same timeouts.
- The core does not use the vendors' SDKs; it opens and closes a connection for each request (`Connection: close`, `native/translation/src/http.rs`). There is no network client or connection pool to close. DNS resolution by the OS has no timeout.
- The runtime timeouts for network translation (connect, read and write; the read timeout applies to each read) are as follows (`native/translation/src/providers/mod.rs`).
    - OpenAI, OpenAI-compatible (cloud), OpenRouter, Groq, Plamo: 5 seconds, 30 seconds, 10 seconds (`CLOUD_CHAT`)
    - Ollama and LM Studio, and OpenAI-compatible at a local or LAN address: 5 seconds, 120 seconds, 10 seconds (`LOCAL_CHAT`, to wait for the first model load)
    - Gemini: 30 seconds each
    - DeepL, Google Cloud Translation, Papago: 5 seconds, 10 seconds, 10 seconds (`MACHINE_TRANSLATION`)
- The Google, Bing and Papago web translators of upstream VRCT cannot be distributed with ASTAROT, so they do not appear in the list of translation engines (`RETIRED_WEB_TRANSLATORS` in `native/core/src/languages.rs`).
- Cloud translation retries once on a temporary error (at most 2 attempts including the first, `Api::attempt` in `native/translation/src/providers/mod.rs`). Errors that are not retried, such as a rejected authentication, fail as they are. Ollama, LM Studio and OpenAI-compatible at a local or LAN address are not retried. If failures continue, a timeout, like any other translation failure, goes on to translating again with CTranslate2.
    - The retry decision and the waits copy into `native/translation/src/providers/retry.rs` the rules of each SDK that the Python backend of 0.4 and earlier used. These are the OpenAI SDK rules (408, 409, 429, 5xx and network failures, `x-should-retry`, `retry-after-ms` and `retry-after`; a wait the server specifies is honored up to 120 seconds, and above that there is no retry; without one, the wait is 0.375 to 0.5 seconds), the DeepL SDK rules (429, 5xx and network failures; the second attempt starts 1 second after the first one started) and the Google SDK rules (Gemini; 408, 429, 500, 502, 503, 504 and network failures; the wait is 1 to 2 seconds, and waits the server specifies are not used). Google Cloud Translation and Papago, which the core added, follow the OpenAI SDK rules.
    - The contract tests in `native/translation/tests/contract/providers.json` confirm that the decisions, waits and backoff are the same as in the Python clients (each SDK) of 0.4 and earlier. Only the use of `LOCAL_CHAT` without retries for OpenAI-compatible at a local or LAN address is recorded as an intended difference (`local-openai-compatible`).
    - When a temperature is set and a chat provider returns 400, the request is sent again without `temperature` (`native/translation/src/providers/chat.rs`). The resend also has retries, so one translation request is sent up to 3 times (4 times if the 400 carries `x-should-retry: true`).
- Requests to Ollama and the chat providers state non-streaming explicitly (`"stream": false`). No thread is created per call for timeouts. A translation request connects on the calling thread, and the connect and read/write waits are limited by socket settings. The DeepL key check is a single request with `DISCOVERY`, and translations are sent with `MACHINE_TRANSLATION`.
- These limit network waits; they are not an upper bound on the total time a translation takes. Data that keeps trickling in, DNS resolution, waiting for the CTranslate2 lock and local inference, and the wait before a retry cannot be interrupted. Failure logs record only the engine name, not the error itself (`native/core/src/controller/translation.rs`). Provider errors are fixed codes and contain no key, URL or request body.

The table below gives a rough estimate of the wait before falling back. It assumes one connect wait and one read wait per attempt and adds them up conservatively as `(connect + read) × attempts + wait before retry`. The value that also adds one write wait per attempt is shown next to it. It does not include DNS, connections that keep making progress, processing time, the resend without `temperature` or retranslation with CTranslate2 (which repeats up to 20 times at 100-millisecond intervals while the local model is loading), so it is not a guarantee of the total time a translation takes.

| Provider | Maximum attempts and wait before retry | Estimate for connect and read waits | Estimate including write waits |
|---|---|---|---|
| OpenAI, OpenAI-compatible (cloud), OpenRouter, Groq, Plamo | 2. Usually 0.375 to 0.5 seconds. Uses the server's `retry-after-ms` or `retry-after` up to 120 seconds | Usually `(5 + 30) × 2 + 0.5`, about 70.5 seconds. Up to about 190 seconds with the server's wait | Usually about 90.5 seconds. Up to about 210 seconds with the server's wait |
| Google Cloud Translation, Papago | 2. The wait follows the OpenAI rules | Usually `(5 + 10) × 2 + 0.5`, about 30.5 seconds. Up to about 150 seconds with the server's wait | Usually about 50.5 seconds. Up to about 170 seconds with the server's wait |
| Gemini | 2. 1 to 2 seconds. The server's wait is not used | `(30 + 30) × 2 + 2`, about 122 seconds | About 182 seconds |
| DeepL | 2. Whatever is left of the 1 second after the first request started (0 to 1 second) | `(5 + 10) × 2 + 1`, about 31 seconds. If the first request takes 1 second or more, the wait is 0 seconds | About 51 seconds |
| Ollama, LM Studio, OpenAI-compatible at a local or LAN address | 1. No wait | `5 + 120`, about 125 seconds | About 135 seconds |

- When translation fails, the text is translated again with CTranslate2. An empty translation of a non-empty source text also counts as a failure. When an LLM response is cut off at the length limit (`finish_reason: length` for OpenAI-compatible, `incomplete_details.reason: max_output_tokens` for the OpenAI Responses API, `finish_reason: MAX_TOKENS` for Gemini, `done_reason: length` for Ollama), the partial translation is dropped and handled the same way as an empty one. When no finish reason is returned, truncation is not guessed from the length of the text.
- In CTranslate2, input longer than 1,024 tokens including special tokens is not run and counts as a failure. Automatic truncation of the input is off, and the output generation limit is fixed at 256 tokens. If the result has no end token, the partial translation is dropped and the existing handling of translation failures follows. The end token is not included in the translation.
- If CTranslate2 can translate the text again, that translation is used and no failure is notified. If it cannot, the source text is used and the result is returned as a failure. The caller switches the engine to CTranslate2 and sends the existing `TRANSLATION_ENGINE_LIMIT` on `/run/error_translation_engine`. When both engines simply do not support the language pair, the source text is used, treated as a success and not notified (`Model.getTranslate`, `Controller._processMessage`).
- When the text is translated into several targets at once and the thread for one target ends abnormally (a panic in the core), that target uses the source text and counts as a failure, as when it cannot be translated again. The translations for the other targets are used as they are. This is not treated as running out of GPU memory, and translation is not turned off. The out-of-memory path (`TRANSLATION_VRAM_*` and `TRANSLATION_DISABLED_VRAM`) is taken only when the engine reports that it ran out of memory.
- A translation is read aloud only when the chosen slot has a real translation that is not empty. The translation result carries a success flag and an origin per slot (`translated`, `failed`, `unsupported`). Neither the source text used on a failure nor the source text treated as a success for an unsupported pair is read aloud. A translation that the translator returned as a success can be read aloud even if it is the same string as the source text. The text fallback and the failure notification stay as described above.
- The OSCQuery capability is decided from whether receiving and advertising are ready. When it becomes unusable, microphone input that had sync on is not resumed automatically. Pausing while the state is unknown, stopping input on failure, restoring settings and the details of notifications follow [The OSC contract](external-interfaces.md#vrchatへのosc).

## Hotkeys and the settings screen

- While the settings window shows the Hotkeys page, all hotkeys are disabled, so that features do not run while keys are being entered. The rest of the settings window pauses nothing (#1236, decided on 2026-11-26). In a browser, where the settings are a page, the hotkeys are disabled while it is open.
- `GlobalHotKeyController` manages all hotkey registration. It watches whether the backend is ready, whether an update is in progress, whether the settings page is open and whether the settings window shows the Hotkeys page, and also the hotkeys confirmed by save responses. Even if a save response arrives after Settings closes, it unregisters the old keys and registers the new ones. Deleted keys are unregistered too. The completion or callback of an old asynchronous registration does not revert the new state.
- Changing or deleting a hotkey sends only the key of the edited action. The edits are kept while waiting for the native conflict check, and duplicates are checked against both the confirmed keys and the keys awaiting a response. When the check finishes, the latest content is checked again, and older edits to the same action are not sent.
- In a hotkey field, Tab and Shift+Tab move focus, and Escape cancels a combination that is only partly entered and goes back to the saved display. These keys are not saved. Losing focus also cancels a combination that is only partly entered. Other key combinations are saved when the keys are released.
- On Wayland, hotkeys are registered through the desktop's shortcut feature (the GlobalShortcuts portal). Elsewhere, Tauri's global shortcuts are used ([External interfaces](external-interfaces.md#ホットキー)).

## Usage presets

- "Used for" at the top of the Settings menu narrows the features shown to fit how the app is used (#554). Several usages can be chosen, and anything that any of them shows is shown (the union). Having none chosen is not possible.
- Usages decide only what is shown. They do not change whether features are on, devices, audio routes or models, and they do not open the microphone.
- The mapping between usages and what they show (main screen switches, pages in the Settings menu) is in one place in the UI, `src-ui/logics/configs/usagePresets.ts`. Appearance, Hotkeys, Updater, Advanced, Experimental and About ASTAROT are shown for every usage.
- Switches that are on, or are in the middle of switching on or off, are shown regardless of usage, so the way to stop a feature is never hidden. The switches for features that the first-run setup prepared are also shown while they are highlighted, until they are turned on ([UC-18](use-cases.md#uc-18-初期設定で基本機能を準備する)). Switches hidden by usage can be shown with "Other features (count)" below the row of switches. Whether they are shown is not saved and does not change settings. Hotkeys, the VR UI and the tray panel still toggle hidden switches as before.
- Hidden pages can still be found with the settings search. A page opened from search or from a button on the main screen appears in the menu while it is open. All items inside a page are shown regardless of usage.
- It is saved in `USAGE_PRESETS` ([Data formats and storage](data-and-persistence.md#その他)). While the value has not arrived, or when it cannot be read, nothing is hidden. A new install starts with "Basic", and an update from an earlier version starts with "Everything".
- The usage names are provisional and will be decided after users try them (Q-14 in #554).

## Experimental features

- Features that were prototyped on the experimental branch and passed testing on real hardware stay on the "Experimental" page in Settings until they graduate to the regular settings (Issue #361). All of them are off by default and run only when the user turns them on with the switches on the page.
- Code that belongs to a feature runs only when the feature is on. The UI checks with `useExperimentalFeature(id)`, and the backend with `experimental_features.is_enabled(config.EXPERIMENTAL_FEATURES, id)`. Both treat features not in the list and values not yet confirmed as off.
- A switch sends only its feature's value with `/set/data/experimental_features` and shows the value confirmed by the response. It is saved immediately, and the format is in [Data formats and storage](data-and-persistence.md#その他).
- When there are no items, the page says that there are no features to try. These cannot be changed from the VR UI (they are not on the list of requests it may relay).
- The VR UI is also listed on this page as a feature under test (Q-05 in #554). However, it is not put in the `EXPERIMENTAL_FEATURES` dictionary; it keeps the existing saved value `OVERLAY_VR_PANEL` and `/set/enable/overlay_vr_panel` and `/set/disable/overlay_vr_panel` as they are. The storage format does not change, so users who had it on keep it on. The action that resets the launcher position appears under it only while the VR UI is on. The "Captions and VR" page holds only a row that leads here.

### Tray icon

- From 0.5.0, the app puts one icon in the system tray when it starts. The icon appears whether or not experimental features are on, and the hexagram overlay uses this one icon too (no separate icon is added).
- The menu has these items: open the main window, turn "Mic input" (the main switch for the microphone's speech recognition) on and off, open ASTAROT's control panel, the monitor for the hexagram, and quit. Each item says what it does without the app open (#1234): the on and off items name the main switch they turn on and off, the control panel item says it is ASTAROT's (not the system's Control Panel), and the monitor item uses the words of the setting on the Experimental page. The control panel and monitor items work only while the hexagram overlay is on, and are grayed out while it is off. The main window sends the item text in the display language. Quit goes through the same shutdown (saving settings) as the main window's close button.
- A left click opens or closes the control panel when the hexagram overlay is on, and shows the main window when it is off.
- The app stays in the tray. The main window's close button (and Alt+F4 and the like) does not quit but puts the window away in the tray. Quitting is done from "Quit" in the tray menu. This holds whether or not experimental features are on. While the window is put away, it is brought to the front when the main window opens a dialog (such as consent for recognition) and when startup fails. It is also brought to the front when a feature toggled from the tray, the hexagram or its panel cannot be used. For a feature whose main screen switch is blocked with a reason, the feature is not toggled and the reason is notified. When the backend refuses, an error notification raised within 30 seconds of the toggle is taken as the refusal.
- Where a tray cannot be created (such as on Linux without the tray library), the app runs without the icon and the close button quits as before (because a window put away could not be brought back). On Linux, the app first checks whether the library can be loaded, and if it cannot, starts without creating a tray. A Linux desktop where the icon can be created but has nowhere to show (such as GNOME without an AppIndicator extension) is handled the same way. On each close, the app checks whether a StatusNotifierWatcher is on the session bus, and quits if there is none. "Close" and "Quit" on the error screen and the startup failure screen also quit instead of putting the window away in the tray.

### Hexagram overlay (`tray_companion`)

- While it is on, the app can start in the tray without showing the main window. The main window is still created, and it keeps starting the backend and driving the desktop captions. Because no way to test this feature has been decided, it was added as an experimental feature, off by default, without going through testing on real hardware on the experimental branch.
- At startup, the Rust side reads `config.json` from the settings folder found by the same rules as the backend. If `EXPERIMENTAL_FEATURES.tray_companion` is `true`, the app starts in the tray without showing the main window. If the file cannot be read or is corrupted, or the value is not `true`, the app starts normally. After startup, the main window switches it with `companion_set` to match the setting's value.
- The control panel has the state (starting, stopped, recognizing), the main screen's feature switches, and a button that opens the main window. It closes on Esc, on its close button and when it loses focus. The switches only call the main window's existing toggles, so the consent and confirmation flows do not change.
- The panel's switches are the same six as the main screen's, in its order and under its names: Translation, Mic input, Listening, Chat reading (OCR), Text to speech (TTS) and Voice changer (RVC) (#1235). Each shows the same state as the main screen's switch, both ways, because the main window owns it and reports every change. A switch the main window cannot turn on does not fail silently. One whose main switch is greyed out says so in the panel and, when pressed, brings the main window forward with the reason. A refusal from the engine is an error notice that brings the main window forward. A dialog the switch opens (consent, a model to set up) brings it forward too, as for the hexagram's labels. A test reads the main screen's list of switches, so a switch added there without the panel fails it.
- While it is on, the desktop captions are shown without changing the saved settings.
- A hexagram magic circle (the shape of the ASTAROT symbol) is hidden at an edge of the screen and operated from there. The edge is chosen with the setting `TRAY_COMPANION_EDGE` (right, left, top, bottom; right by default), which appears under the hexagram overlay switch on the Experimental page. The edge is the edge of the work area (inside the taskbar), and the hexagram appears at its middle.
- The monitor is chosen with the setting `TRAY_COMPANION_MONITOR`. The value is the name the system gives the monitor (such as `\\.\DISPLAY2` on Windows), and when it is empty, the OS's primary monitor is used (the default). It can be chosen on the Experimental page (under the edge choice) and from "Monitor for the hexagram" in the tray menu. The monitors are shown with numbers from left to right and top to bottom.
- If the chosen monitor is disconnected, the value is kept, and in the meantime the hexagram appears on the primary monitor. When the monitor is connected again, the hexagram goes back to it. The settings page and the tray menu list it as a monitor that is not connected. While the feature is on, the monitor list is read again every 2 seconds, and the tray menu is rebuilt when it changes.
- While the hexagram is hidden, its window is not shown, so it does not block clicks in the game. The Rust side looks at the pointer position more than ten times a second, and when the pointer comes near the middle of the edge, it shows half of the hexagram with its center on the edge. It shows only when the pointer stays for 0.16 seconds in a band within about 14 px of the edge. If the distance from the edge changes by more than 4 px (logical) inside the band, the wait starts over. A pointer that slowly crosses the border with a neighboring monitor does not bring it out (#563). About 0.45 seconds after the pointer leaves the window, it hides again. The window does not take focus.
- The hexagram's 6 triangles match the 6 switches on the main screen (Mic input, Translation, Text to speech, Voice changer, Listening, Chat reading) and show the same icons as those switches. The triangle of a feature that is on has Lilac edges and a Lilac icon, with a pale Lilac fill (#536). The 3 triangles that face the inside of the screen are visible, and one notch of the mouse wheel turns the hexagram 60°, which changes the visible set by one.
- Resting the pointer on a visible triangle opens that feature's label toward the center of the screen. Pressing a triangle or a label runs the same toggle as that switch on the main screen. Pressing a triangle opens the label at once, without waiting for the pointer to stay, and the label shows what happened (#536). Resting the pointer alone toggles nothing.
- After a triangle or a label is pressed, until the main window returns the switch state (4 seconds at most), the label shows "Switching…", and neither the triangles nor the label can be pressed. If the request could not be sent to the main window, the label shows "Could not switch" for 3 seconds. When a switch turns on or off, its triangle flashes briefly. The same happens when it was changed from the main screen or with a hotkey (#536).
- Only the first time the hexagram comes out, a hint shown for 5 seconds toward the center of the screen says that turning the wheel brings out the other 3. It goes away early when the wheel turns or a label opens. The main window saves that the hint was shown in the setting `TRAY_COMPANION_WHEEL_HINT_SHOWN`, and it is not shown again. It is not shown until the main window has received the settings (#536).
- The hexagon in the center is assigned to common settings. Resting the pointer on the center opens the common settings label toward the center of the screen. It holds 3 items, switching the edge where the hexagram hides (which saves `TRAY_COMPANION_EDGE`), opening the main window and opening the control panel, and each acts only when pressed. Pressing the center also opens the control panel next to the hexagram (toward the inside of the screen).
- The triangles and the center open their label when the pointer stays for about 0.18 seconds. Crossing a triangle while moving from the center to its label does not change the label.
- Turning the feature off clears away the panel and the hexagram, grays out the overlay items in the tray menu and shows the main window if it was hidden. While it is off, neither the panel nor the hexagram is created, and the pointer is not watched. Overlay commands are refused, and only the commands for the tray (receiving the state and text, passing on requests from the menu) are accepted.
- The panel and the hexagram receive only switch states and UI text. Recognized speech and typed text are not passed to them, and are not written to logs.

# 横断的な振る舞い（日本語版）

複数の機能にまたがる決まりをここに集める（arc42の「Crosscutting Concepts」にあたる）。機能ごとの文書は、ここに書いた決まりを繰り返さず参照する。

## エラーの扱い

エラーがUIに届く経路は4つある。

| 経路 | 形 | 例 | UIでの見せ方 |
|---|---|---|---|
| 要求への400応答 | `{"status": 400, "result": {"error_code", "message", "data", …}}` | 設定値の検証、APIキーの拒否 | `errorHandling_Backend`（`src-ui/logics/_useBackendErrorHandling.ts`）が`data`で画面の値を戻し、翻訳した文言を通知で出す |
| サイドカーからの400通知 | 同じ形で`/run/error_…`などに届く | VRAM不足、入力デバイスなし、翻訳エンジンの上限 | 同上。オンにした機能を自動でオフにした場合は、そのスイッチの表示も戻す |
| 認識エラーの通知 | 200の`/run/transcription_recognition_error`に`{error_code, stage, source, message, recoverable}`。クラウドのエンジンが失敗の理由を返したときは、中核が`cause`（`TRANSCRIPTION_API_AUTH_FAILED`・`_RATE_LIMITED`・`_TIMEOUT`・`_SERVER_ERROR`）を足す。`error_code`は`ASR_ERROR`のまま | 音声認識の失敗 | 会話ログにシステムメッセージとして残す。`cause`に`backend_errors`の文言があればそれを、なければ`backend_errors.<コード>`の文言を出し、`<コード>_mic`・`<コード>_speaker`があれば`source`に合うほうを使う。文言がなければ英語の`message`を出す |
| 機能ごとのエラー状態 | 409などで`{"error_code": …}` | 読み上げ、RVC、音声サーバー、モデル取得、リアルタイム音声認識 | 各設定画面の状態欄に、`error_code`に対応する文言を出す |

- 404・423・500と送信失敗では、通常の制御の待機を解除して最後に確認した値へ戻す。500では対応する読み取り先から状態を再取得する。書き込みの自動再送や、時間だけを根拠にした待機解除は追加しない。専用の対応づけを持つ言語・音声・モデル取得とサイドカー終了時の扱いは[IPCプロトコル](ipc-protocol.md#失敗した要求の待機を解除する)を参照する。
- OBSの有効化・ポート変更と、それに伴うWebSocketホスト変更の400応答では、`data`に要求元の設定の変更前の値を返す。UIもエラーコードではなくエンドポイントで戻す設定を選ぶ。例えばOBS有効化中のポートエラーはOBSのスイッチへ偽を返し、ポート変更中の再起動エラーは元のポート番号を返す。通知は原因のコードに対応する文言を表示し、復旧に失敗して無効になったサービスがあるか、WebSocketとOBSの有効状態を読み直す。
- 想定外の例外は500になり、UIは再起動を勧める通知を出す。stderrに警告以外の行が出たときも同じ扱いである。
- IPC応答のJSONは`NaN`・無限大を許可しない。直列化できない値が混入した場合は、既存の直列化失敗時の500応答に置き換え、JSONとして読める応答を返す。
- `errorHandling_Backend`に分岐のないエラーコード（`GENERAL_*`を含む）と500は、汎用の通知（`common_error.unexpected_error`）になる。画面にはエラーコード（500ではエンドポイント）と、再起動とIssuesでの報告を勧める文だけを出し、例外の文はコンソールに出す。新しいエラーコードを足すときは、UIの分岐と`locales/`の`backend_errors.<コード>`の文言も足す。分岐のある通知はこの文言を出し、文言がなければ英語の`message`を出す。どのコードに分岐があるかは[エラーコード一覧](reference/error-codes.md)の「UIの個別処理」列で確かめる。
- 通知（トースト）は種類ごとに`category_id`を持ち、同じ種類が重ならない。既定では5秒で消え、マウスを重ねている間は止まる。
- エラーの文言は「何が起きたか」と「どうすればよいか」を書く。英語の`message`はログ向けで、画面にはそのまま出さない。

## メッセージの受付と出力

- 会話ログの再送は、主ポインターの主ボタンを500ms押し続けた場合だけ行う。離す、範囲外へ移動する、操作が取り消される、ポインターのキャプチャーやフォーカスを失う、コントロールが消える場合は待機を取り消す。古いタイマーが後から実行されても送信しない。通常のクリックは入力欄への再編集を保つ。
- 入力欄・Quick Chat、従来とリアルタイムの文字起こし、OCRは、受付時の設定を1つの変更できないスナップショットにする。元の言語、翻訳先の有効な枠と言語、翻訳のオンオフ、エンジンとCTranslate2の重み、ひらがな・ローマ字、訳だけを送る設定、VRのログに訳だけを出す設定、表示書式を、翻訳から読み上げ選択まで共通で使う。リアルタイムの確定結果は待ち行列に入る前に固定し、VRの大きいログの確定と訳つきの字幕もそのスナップショットで描く。途中の字幕は届くたびにその時点で固定する。処理中に設定を変えても、訳の配列と枠の対応、OSCの文面、オーバーレイとWebSocketの言語情報を混ぜない。VRのログは描く時点で設定を読み直さない。遅れて翻訳が失敗しても、その間に選び直した言語やエンジンは戻さない。
- VRChatへの送信、各オーバーレイ、クリップボード、WebSocket、会話ログの出力スイッチは固定しない。各出力の直前に現在の状態と配送世代を確かめる。OSCは送受信先の変更を待つロックを取得した後、UDP送信の直前にも確かめ、省略した送信では順序の番号を進めない。描画後も確かめる。読み上げは受付時の設定に加え、既存の音声世代・入力元の世代による取り消しを守る。
- クリップボードへの出力（音声タイピングモード）は、文をクリップボードへ入れてから、SteamVRで動いているアプリのウィンドウを前面に出し、Ctrl+Vを送る。前面に出せなかったときはコピーだけ行う。貼り付け先は貼り付けのたびに決める。SteamVRのシーンのアプリのうち、キーが`steam.app.`で始まるものの名前でウィンドウを探す。SteamVRが動いていない、つなげない、そのようなアプリがないときはコピーだけ行う。名前を読むOpenVRの接続はオーバーレイと共有し、オーバーレイが使っていなければ読んだあとに閉じる。Linuxでは、X11／XWaylandのウィンドウ（Protonで動くVRChatなど）だけが貼り付け先になる。前面に出す依頼は`_NET_ACTIVE_WINDOW`、キーはXTestで送る。KDE Plasma（Wayland）は、アプリが初めてキーを送るときに「Remote Control」の確認を出す。許可はX11の接続ごとなので、接続を使い回す。Waylandネイティブのウィンドウには貼り付けない。
- 字幕オーバーレイは、画像をバイト列にした後と再送の直前にも、配送世代・出力の有効状態・OFFによる失効を確かめる。転送失敗時は、現在も有効な要求だけが所有スレッドに再接続を頼める。再初期化を待つ上限は5秒で、再送は1回までとする。有効な要求の再送が失敗した場合や再初期化が時間切れになった場合は、出力先の例外として下記の`/run/message_output_error`で知らせる。停止・無効化・世代の更新で失効した要求には、このエラーを出さない。大きい字幕の履歴は転送に成功したときだけ確定し、失効・失敗した更新は戻す。OFFでは先に出力を無効にし、転送と消去を同じロックで順に処理する。リアルタイム認識の終了処理は履歴を整理するが、大きい字幕がOFFならその履歴を表示しない。サンプル文も描画後に有効状態を確かめる。
- マイクの訳文を読み上げの待ち行列に入れる直前には、翻訳が引き続きオンで、選択中のタブと読み上げ対象の枠の言語・地域・有効状態が受付時と同じかも確かめる。一致しなければその文の読み上げを省略し、エラーは出さない。テキストの配送は受付時の設定で続ける。
- マイクの原文は、その確定発話の翻訳を始める前に読み上げの待ち行列に入れる。翻訳のスイッチは、マイクの原文読み上げを取り消さない。
- チャットボックスへ送れる入力には、全入力元で共通の増加する番号を受付時に付ける。対象は入力欄・Quick Chat、従来とリアルタイムのマイク、送信設定が有効な従来のスピーカーである。リアルタイムのマイクは確定結果を受け取った時点で付け、翻訳の待ち行列で待つ間に打った入力より前の番号にする。OSCの比較と送信を直列に行い、より大きい番号の送信が既に成功していれば古い文は送らない。他の出力とログへの記録は続け、UIの行も失敗にしない。省略は本文を含めず`process.log`に記録する。番号は送信に成功したときだけ進め、待ち時間や送信頻度の制御は加えない。リアルタイムのスピーカーとOCRは従来どおりOSCへ送らない。
- 出力の順序は、チャットボックス、訳文の読み上げの依頼（TTSと、マイクの訳文の読み上げ）、VRのオーバーレイ、クリップボード、UI、WebSocket、会話ログとする。読み上げは、時間のかかるVRのオーバーレイの描画を待たずに頼む（#556）。
- 出力先が例外を返しても、残りの出力先への処理を既存の順序で続ける。例外を`errorLogging`で記録し、`/run/message_output_error`の400通知で`MESSAGE_OUTPUT_FAILED`と出力先を知らせる。これはメッセージ送信への失敗応答ではない。通常の200応答・通知を維持し、文字起こしを止めず、自動で再送しない。UIは出力先ごとの警告を表示し、再送すると既に届いた内容が重複する可能性を知らせる。ペイロードは[データ形式](data-and-persistence.md#メッセージ)を参照する。
- リアルタイムの確定字幕は配送結果を待って行を確定する。期限切れ・失効や、チャットボックスの順序による省略は、処理失敗と区別して示す。ただし、既に出力が成功した行を未送信には戻さない。停止後も表示済みの行への`outcome`通知だけは出し、新しい本文や出力を配送しない（[通知と行の状態](data-and-persistence.md#リアルタイム字幕と配送結果)）。

## 設定の保存

### 画面での保存のしかた

| 操作の種類 | 保存のタイミング | 例 |
|---|---|---|
| スイッチ、ラジオボタン、選択欄、スライダー | 操作した時点で`/set/data/…`を送る | 透明度、UIの言語、翻訳エンジン |
| 文字の入力欄（設定画面） | Enterを押すか欄からフォーカスが外れたとき、欄の検査で受け付けた値を保存する | OSCのポート、APIキー、URL |
| 組の欄（TLSの証明書と秘密鍵、アドレスとそのキー、TTS、RVC、音声サーバー、音声経路、リアルタイム字幕、メッセージ書式のフォーム） | 選択、スイッチ、一覧の変更はすぐ、スライダーは離したとき。打った文字はEnterか、フォーカスが組の外に出て組の全部の欄を受け付けられるとき | 声の名前、モデルのパス |

どの設定も自分で保存し、保存のボタンはない（#1111）。About以外の設定のページは、上のバーで変更がすぐに反映されることを伝える（`DESIGN.md`）。

- 文字の欄でEscを押すと、保存してある値に戻す（組では組の保存してある値）。
- APIキーなどの認証情報は、空のまま欄を離れても保存してある値を残す。消すのは空の欄でEnterを押したときだけ。
- 欄が断った値は送らない。何が違い、どんな値ならよいかを欄の下に出し、欄を正しくない印にする。欄自身の保存を中核が断ったときもそのエラーコードの文でそこに出し、通知は重ねて出さない。同じエンドポイントでの中核のほかの知らせは通知のまま。
- 欄と組は、送った要求への成功応答で保存を確定する。送信失敗・拒否・応答待ちの期限切れでは確定せず、編集内容を残して直してから保存し直すか、Escで戻せる。確定済みの値は失敗した編集で上書きしない。保存に失敗した単語フィルターは保存してある一覧に戻し、そのことを伝える。
- 保存を待つ間も欄は使え、その間の変更は待っている保存が終わってから保存する。
- 「保存しました」の通知は出さない。断られた値や保存していない値のままページを移るか設定を閉じると、その値は捨て、先に何も聞かない。
- RVCページでRVCを選ぶのは専用のボタン。ページを開いただけでは何も保存しない。
- 音声・RVC・音声サーバー・リアルタイム音声認識のフォームは、自分が送った保存要求への成功応答で保存を確定する。辞書の空白などが正規化された場合は、返された値を採用し、送信後に編集した項目だけを残す。状態の再取得や別の保存要求への応答では確定しない。5秒以内に応答がなければ未確認として編集を保ち、その要求への遅い成功応答は受け付ける。破棄や再保存の後に届いた古い応答では、新しい編集を確定しない。

- TTS、音声経路、TTS出力先のフォームは、`/set/data/voice_settings`に変更した項目だけを送る。サイドカーは音声設定のロック内で現在の設定に重ね、全体を検証してから経路の切り替えと保存を行う。省略された項目は保持し、成功応答には設定全体を返す。経路変更時の直接音声の停止条件は変えない。

### サイドカーでの保存

- 値は検証してから保存する。検証に通らない値は400の`VALIDATION_…`で返し、保存しない。複数の項目を持つ値（言語の組など）は、項目ごとに無効なものだけを元の値に戻し、エラーにしないものがある。
- `config.json`への書き込みは、最後の変更から2秒後にまとめて行う。ウィンドウの位置、メッセージ欄の比率、ホットキーはすぐ書く。
- 書き込みごとに、保存先と同じディレクトリに名前の重複しない一時ファイルを排他的に作成する。POSIXでは権限を0600にし、書き込みと`fsync`が終わってから`os.replace`で置き換える。既存の一時ファイルやシンボリックリンクは使わず、後片付けもその保存処理が作ったファイルだけに行う。途中で落ちても`config.json`は壊れない。
- 保存値の取得からファイルの置き換えまでを同じロック内で行う。実行中の遅延保存が、後から成功した即時保存を古い値で上書きしない。同じ保存先を使う複数のサイドカーは`config.json.lock`のOSロックで保存を直列化する（POSIXは`flock`、Windowsはバイト範囲ロック）。ロックファイルは削除しない。別プロセスの設定変更をマージする仕組みではなく、最後に保存した完全な設定が残る。
- 保存値の取得に1つでも失敗したら、一部だけの設定は保存しない。JSONの直列化でも`NaN`・無限大を拒否し、失敗時は最後に保存できたファイルを保持する。この場合の通知と再試行は書き込み失敗と同じで、`reason`は`write_failed`である。
- 書き込みに失敗したとき（容量不足、権限、読み取り専用など）は、変更をメモリーに残したまま`/run/config_save_failed`に`{reason, path}`を送り、30秒ごとに書き直す。`reason`は`disk_full`、`permission_denied`、`read_only`、`write_failed`のどれかである。UIは消えない通知を出す。書き直せたら`/run/config_save_recovered`を送り、UIは保存できたことを知らせる。失敗が続く間の通知は最初の1回だけである。
- 再試行も失敗した場合は次の30秒後の再試行を予約し、保存できるまで続ける。保存に成功したら未実行の再試行を取り消す。
- 初期化と保存済み設定の読み込み・適用が終わるまでは、即時保存も遅延保存も行わない。読み込みが中断した場合や、元のファイルを読み取れない・退避できない場合は、元のファイルを置き換えず、`/run/config_save_failed`の`reason: load_failed`で知らせる。この場合は自動で書き直さず、ファイルの内容や権限を直して再起動するまで保存を止める。
- 詳しくは[データ形式と保存](data-and-persistence.md)。

### APIキーの変更

- OpenAI互換とCustom WhisperでURLを変更し、キーを入力した場合は、キーが保存済みの値と同じでも、`/set/data/openai_compatible_auth_key_and_url`または`/set/data/custom_whisper_auth_key_and_url`へ`{url, auth_key}`を1回だけ送る。入力した組み合わせで認証とモデルを確認し、成功したら両方を反映する。失敗時はどちらも変更しない。成功応答も`{url, auth_key}`で返し、空のキーは`null`にする。キーが空なら認証せず、URLの保存とキーの削除をまとめて行う。
- 組の保存も同じサービスのFIFOと共有ロックを使う。URLが不正なら既存のURLエラーで保存済みURLを`data`に返し、認証・モデル確認の失敗なら既存の認証エラーで保存済みキーを返す。画面は自分の要求への応答で保存を確定し、失敗した編集は残す。
- URLだけの変更要求では、検証後のURLが保存済みの値と異なり、キーが保存されていれば、外部へ通信せず何も変更しない。400と`CREDENTIAL_REENTRY_REQUIRED`を返し、`data`には保存済みURLを入れる。同じURLなら通信も保存もせず200を返す。キーが未設定ならURLだけを保存する。キーだけの編集・削除も既存のエンドポイントを使う。
- 画面では、前後の空白を除いてURLが保存済みの値から変わったらキー欄を空にする。利用者が入力したキーは上書きせず、入力していなければURLを元に戻したときに保存済みキーも戻す。URLが異なり、保存済みキーがあるのにキー欄が空の間は保存を止め、新しいURLで使うキーの入力を案内する。キー不要のサーバーでは、先に保存済みキーを削除してからURLを変える。「破棄」では両方の保存値を戻し、保存失敗時は編集を残す。

- 翻訳と文字起こしのキーは、認証、利用可能なモデル一覧、選択するモデルを確かめてから保存する。翻訳では新しいクライアントの初期化も先に終える。モデル一覧を持たないDeepLは、新しいクライアントで認証を確かめる。
- 確認中は、それまでのキー、利用可能な状態、モデル一覧、選択モデル、翻訳クライアントを保つ。認証後でも、モデルがない、モデルを選べない、クライアントを初期化できない場合は変更しない。既存の`AUTH_…`または`TRANSCRIPTION_API_AUTH_FAILED`を返し、`data`には保存済みのキーを入れる。
- 同じサービスのキーの変更・削除、モデル選択、OpenAI互換・Custom WhisperのURL変更は受信順に処理する。認証確認が遅れても、後のモデル選択を古い選択で上書きしない。確認中に選択モデルが変わった翻訳クライアントも反映せず、保存済みキーをエラーの`data`に返す。
- サービスへの問い合わせは共有ロックの外で行う。確認がすべて終わったら、共有のロック内で対象のキーだけを更新し、準備したクライアントと設定を反映する。キーの削除も同じロックを使う。別のサービスのキーを同時に変更しても、その変更を上書きしない。ファイルへの保存時期は通常の設定と同じである。
- OpenAI互換のURL単独の変更は、上記のキー再入力の規則に従う。不正なURLには`CONNECTION_OPENAI_COMPATIBLE_URL_INVALID`を返し、`data`には保存済みURLを入れる。キー、利用可能な状態、モデル一覧、選択モデル、動作中のクライアントは変更しない。
- OpenAI互換のキー、またはURLとキーの組を確認している間に関連設定が変わった場合、古い組み合わせのクライアントは反映せず、認証エラーを返す。
- Custom WhisperのURL単独の変更にも同じ規則を適用する。不正なURLには`CONNECTION_TRANSCRIPTION_CUSTOM_URL_INVALID`を返し、`data`には保存済みURLを入れる。キー、利用可能な状態、モデル一覧、選択モデルは変更しない。

## 同意と外部への送信

- モデルの取得は、名前、提供元、正確な容量、ライセンスを画面に示し、利用者がチェックして開始したときだけ行う。カタログは版、サイズ、SHA-256、ライセンスを固定する（`native/ops/src/downloads/catalog.rs`）。ローカル翻訳（ONNX Runtime）のモデルも、公開したあとはカタログの対象`translation`から同じ確認を経て取得する（0.4までのCTranslate2の固定の重みの取得は0.5.0で引退した）。別リポジトリやHubキャッシュからの暗黙の取得は行わない。
- お使いのPCに取得済みのモデルは、確認の画面も同意も挟まずに、カードから使う（#1263）。何も取得しないためで、同意と確認はダウンロードのときに済んでいる。`/run/check_model_download`（`{id, catalog_version}`）がファイルの容量とSHA-256を照合し、通信はしない。一致しないファイルはそのまま残し、ジョブは`model_files_changed`で失敗する。カードは取得の確認を出し、もう一度ダウンロードする前に同意を求める。お使いのPCにないモデルは409の`model_not_downloaded`で断る。照合が済むと、カードがダウンロードの「適用」と同じくモデルを適用する。モデルがそろってから先へ進む呼び出し元（音声認識の直し、#1232）は、自分で適用する。
- 設定のカタログで取得したモデルは、取得の準備ができたら適用する。初期設定がモデルを適用するのと同じ形である（#1308 ★3、2026-11-28の決定）。そのモデルのサーバーや機能が動いているときは、準備ができたまま「モデルパスを適用」と理由を出す。音声認識のモデルは、代わりにspeech.cppの区分の「マイク入力のモデル」と「聞き取りのモデル」で入力ごとに選ぶ（#1308 ★1）。どちらも、お使いのPCにある認識モデルから選び、上と同じく照合してから、その入力だけに適用する。カードはモデルを取得し、どの入力が使っているかを示す（「使用中（マイク入力）」「使用中（聞き取り）」）。お使いのPCにあり、まだ使っていない入力がある認識モデルは、カードにも「このモデルを使う」を出し、カードのどこを押してもそれを押したことになる。押すと「マイク入力に使う」「聞き取りに使う」の小さなメニューを開く。すでにそのモデルを使っている入力は、そう示して選べない。項目を押すと、欄と同じ照合と適用で、その入力だけにモデルを適用する。認識のサーバー（マイク入力のもの、聞き取りだけのもの）が動いている間と、パスに保存していない編集があるときは、メニューが理由を示し、項目は待つ。両方の入力が使っているカードには押すものがない。2つの欄はそのまま残す。取得した認識モデルが自動で適用されるのは、マイク入力のモデルがまだないときだけで、マイク入力のモデルになる。認識モデルが設定され、音声認識のエンジンが未選択なら、speech.cppを選ぶ。
- 非商用のライセンスのモデル（NLLB-200など）は、同意とは別に非商用に限ることの確認を求める（#411）。カタログの行の`restrictions`はライセンスの文字列から決まり、Creative CommonsのNonCommercialなら`["non_commercial"]`になる。Gemma Terms of Useを含むライセンスの翻訳のモデル（TranslateGemma）は`gemma_terms`を持つ（ADR-015）。読み上げのIrodori-TTS v4 LargeもGemma Terms of Useに従うが、この確認は付かない（翻訳のモデルだけに限ると2026-11-19に決めた）。確認の画面はライセンスの名前と制限の中身を示し、同意の下に種類ごとのチェックを出す。`gemma_terms`では、Gemmaの利用規約と禁止用途のポリシーがモデルを使う人にも及ぶことを示す。`/run/start_model_download`の要求は`{id, consent, catalog_version}`に、確かめた種類の`acknowledged`を足す。欠けていれば400の`model_download_restriction_unacknowledged`、知らない種類や重複やそのモデルにない種類があれば400の`download_request_invalid`で断り、ファイルを書かず通信もしない。制限のないモデルの要求は変わらない。確認は`receipt.json`にも設定にも記録しない（[モデル取得](../voice-stack/model-downloads.md#非商用のライセンスの確認)）。
- ローカル翻訳のモデルのカードには、翻訳の間に使うメモリを示す（`guidance.reference_memory_bytes`）。測っていないモデルは「まだ測っていません」と示し、数値を作らない。翻訳の計算に使う機器（`SELECTED_TRANSLATION_COMPUTE_DEVICE`）がCPUならRAMの総量と、GPUならそのGPUのメモリの総量と比べる。RAMと比べるときはOSとVRChatの分（13 GiB）を、GPUと比べるときはVRChatの分（4 GiB）を残した量と比べる（読み上げや音声認識のモデルも同じ）。足りなければカードと取得の確認画面に性能不足の可能性を出す。目安なので選ぶことも取得も止めない（#405、#597、[モデル取得](../voice-stack/model-downloads.md#性能不足の可能性の警告405)）。
- 取得済みモデルのパスを適用する際の再検証は、Applyの応答待ちでも同じモデル・ジョブのキャンセルを受け付ける。Applyとキャンセルの応答は別々に待ち、片方の応答で他方の待機を解除しない。待機中は別の適用や取得を開始できない。10秒間応答がなければ警告を表示し、Applyを含むすべての待機を解除する（#563）。応答が失われても、ほかの操作がアプリを起動し直すまで止まったままにはならない。解除したとき、そのジョブがまだ検証中（`verifying`、`cancelling`）のこともある。その間に送った取得や別の適用は、中核が `download_busy`（別のモデルを取得中）で断るので、検証と重ならない。そのジョブのキャンセルは受け付ける。
- 翻訳のモデルは、ほかのモデルと同じカタログの確認と同意で取得する（[モデル取得](../voice-stack/model-downloads.md)）。保存済みの選択、NLLBの利用条件への選択時の同意、起動時取得のスイッチだけでは取得に同意したことにならない。NLLBは非商用の制限を必ず表示し、既定にしない。0.4までの内蔵モデル（CTranslate2）の取得要求とその同意（`consent: true`と`manifest_version`）は、中核では0.5.0で、画面では#1015でなくなった。
- 起動時にモデルを自動では取得しない。起動時の自動取得（`AUTO_DOWNLOAD_MODELS`）は 0.5.0 で旧 CTranslate2 の重みと一緒に引退した（[中核の統合](../voice-stack/core-integration.md)）。設定のキーと`/get/data/auto_download_models`などのエンドポイントは互換のために残すが、中核は値を読まず、設定画面にスイッチを出さない。取得は、設定や確認画面で利用者が同意した明示の取得だけで行う（[モデル取得](../voice-stack/model-downloads.md)）。
- 翻訳の有効化・推論・取得済み判定で使うtokenizerは、容量とSHA-256を検証した固定ファイルだけを専用の一時フォルダーへコピーし、`local_files_only=True`で読む。ファイルがないか照合に通らなければ`TRANSLATION_MODEL_MISSING`を返す。ファイルは照合に通ったのにtokenizerを組み立てられなかったとき（Transformersを読み込めない、読み込みの途中で失敗した）は`TRANSLATION_MODEL_LOAD_FAILED`を返し、通知で知らせる。取得し直しても直らない失敗を`TRANSLATION_MODEL_MISSING`にすると、確認画面で同意するたびに同じ画面へ戻る。UIは、翻訳のスイッチを押した結果として`TRANSLATION_MODEL_MISSING`が返れば、その場で取得の確認画面（提供元、ライセンス、容量、同意）を開く。同意して取得が終わると、UIが翻訳をもう一度オンにする。このことは確認画面に表示する。取得を取り消したとき、失敗したとき、会話欄の「取得内容を確認」から開いたときは、翻訳をオンにしない。スイッチ以外の要求で返ったときは、通知で知らせる。モデルがまだないのは最初の起動では当たり前の状態なので、`TRANSLATION_MODEL_MISSING`は`error.log`に残さず、利用状況の`error`にも数えない（`ERROR_METADATA`の`"reported": False`）。`TRANSLATION_MODEL_LOAD_FAILED`は両方に残す。固定版をネットワークから取得するのは、同意済みの明示的な取得と、記録済み同意を持つ起動時取得に限る。
- CTranslate2の推論では、メッセージ受付時の重みと読み込み済みの重みを照合する。違う場合は、直前の読み込みと同じ保存先・デバイス・計算形式で、受付時の重みをローカルから読む。重みの切り替えと推論は同じロックで保護し、モデル・tokenizer・言語コードを混ぜない。切り替え前に受け付けたメッセージは、元の重みで処理する。
- CTranslate2の重み・tokenizerの検証や計算形式の決定に失敗した場合は、使用可能な元のモデルを保つ。準備が済んだら元のモデルを解放してから次を確保し、確保に失敗した場合は未読み込み状態にする。CTranslate2またはTransformersが使えない場合は、有効化を成功にせず既存の読み込みエラーを返し、翻訳をオフのままにする。
- 内蔵の既存モデルも全固定ファイルの容量・SHA-256を検証してから利用する。検証記録はmanifestとファイルの変更に結び付け、ロード成功だけの旧記録を使わない。新旧名の競合や不一致でユーザーファイルを削除しない。rootのOS lease、専用staging、転送中の容量上限、ファイルごとの期限、終了時の取消・join、識別付きの終了通知を使う。終了時は全入力元の配送を失効させ、カタログ取得・Applyと内蔵モデル取得の両方に取消を通知した後で、期限付きの待機を行う。詳細は[モデル取得の契約](../voice-stack/model-downloads.md#内蔵モデルの検証保存終了)を参照する。
- クラウドの翻訳エンジンと音声認識エンジンは、利用者がエンジンを選んだときだけ使う。キーが必要なサービスではキーの登録も必要である。選んだ時点で、そのサービスへの送信に同意したとみなす。キーなしで使えた Google の Web 音声認識は、非公式の窓口と汎用のキーを使っていたので外した。
- LLMでの翻訳では、現在の本文だけでなく、プロンプトと直近の会話履歴も選んだサービスへ送る。付属の設定ではチャット・マイク・スピーカーの最大5件を含む。実行環境の情報は`User-Agent`のほかに送らない。送る内容と履歴の制限は[LLMでの翻訳](external-interfaces.md#llmでの翻訳)を参照する。
- 翻訳エンジン・接続先・モデルを変えたら、それまでの翻訳用履歴を無効にする。元の送信先に戻しても復元しない。翻訳がオフの間の会話や、変更前に受け付けて変更後に処理が終わった会話を、新しい履歴に入れない。画面の会話ログや保存済みのログは消さない。
- 新規設定の音声認識エンジンは未選択とする。従来の文字起こしを未選択のままオンにすると、録音を開かず400の`TRANSCRIPTION_ENGINE_NOT_SELECTED`を返す。UIはローカル（speech.cpp）を選ぶか、エンジンの設定を開いてクラウドのエンジンを選ぶ画面を開く。ローカル（speech.cpp）を選ぶと、選択の保存応答を確認してから利用者の元のオン操作を続ける。エンジンの設定を開いたとき、キャンセルや保存失敗では開始しない。ローカル（speech.cpp）の認識モデルや VAD モデルが設定されていなければ、そのオン操作が下のリアルタイム経路の`TRANSCRIPTION_SEND_NOT_READY`／`TRANSCRIPTION_RECEIVE_NOT_READY`（`details.reason`は`realtime_asr_model_missing`または`realtime_vad_model_missing`）で知らせる。モデルは、設定の「音声認識（ASR）」か下のスイッチの直し方から、内容を確認し同意したときだけ取得する。この画面からは取得しない。
- 選択した音声認識エンジンから別のエンジンへ自動では切り替えない。API認識器を構築できなければ`TRANSCRIPTION_ENGINE_UNAVAILABLE`でエンジン設定へ案内する。認識器の初期化は録音デバイスを開く前に行う。保存済みの Google の選択は、読み込むときに未選択に戻す（[保存形式](data-and-persistence.md#音声認識エンジンの選択)）。
- Linux のメインのマイク／聞き取りスイッチは、上の選択とは独立したローカル speech.cpp リアルタイム経路を使う。この選択画面を挟まず、従来の準備確認と利用者のオン操作を必要とする。Windows のスイッチは、音声認識エンジンにローカル（speech.cpp、`SpeechCpp`）を選んでいるときだけこの経路を使い（サーバーはリアルタイム音声認識の設定の同梱または外部）、クラウドのエンジンでは従来の録音を使う。エンジンを変えて経路が変わると、それまでの経路で動いていたスイッチをオフにする。従来の録音のまま別のエンジンに変えたときも、動いていた文字起こしのスイッチをオフにする。前のエンジンへは送り続けない。もう一度オンにすると新しい経路またはエンジンで始まる。
- メインのマイク入力や聞き取りのスイッチが、音声認識に足りないものがあって断られたときは、設定の場所を示す通知ではなく、スイッチのところで直し方を示す（#1225、2026-11-26の決定）。`realtime_asr_model_missing`と`realtime_vad_model_missing`では、最初のセットアップへ導く。セットアップは取得するモデルとその大きさを示し、同意したときだけ取得する。`realtime_language_auto_unsupported`と`realtime_language_unsupported`では、断りに`details.languages`（そのモデルが受け付ける言語）も付く。その中から言語を選ぶとその入力の言語として保存し、保存した設定が戻ってからスイッチをもう一度オンにする。モデルが言語を判定できず、サーバーが同梱のものなら、判定できるモデルもダウンロードのカタログの確認（大きさ、ライセンス、同意）を通して勧める。カタログが判定できると示し（`detects`）、いちばん多くの言語に勧めるもので、いまはQwen3-ASR 0.6Bである。取得が終わると、断られた入力だけに適用し、スイッチをオンにする（#1242）。マイク入力ならマイク入力のモデルとして、聞き取りなら聞き取りだけのモデル（`listening_model`、`"source": "speaker"`）として適用し、マイク入力のモデルはそのままにする。`realtime_asr_models_do_not_fit`（聞き取りのモデルがマイク入力のモデルと一緒に収まらない。2026-11-27の決定）では、両方で1つのモデルを使う道を示す。聞き取りだけのモデルを外し、保存した設定がそれなしで戻ってから、聞き取りをもう一度オンにする。ASRサーバーや字幕が動いている間に適用が断られたとき（`model_target_busy`）はそれを知らせ、何もオンにしない。同梱サーバーが起動しなかったときや止まったとき（`speech_server_*`の理由、#1308 N-14）は、ダイアログがスイッチの言葉で理由を伝える。使用中、時間切れ、途中の終了、動いていないとき（`speech_server_busy`、`speech_server_start_timeout`、`speech_server_exited`、`speech_server_not_ready`）は「もう一度オンにする」を示し、モデル、デバイス、ドライバーで失敗したときはサーバーの設定を開くことを主な操作にする。同梱のspeech.cppが見つからないか検査に通らないとき（`speech_bundle_missing_or_invalid`。スイッチの開始でもこの理由を残す。#1314）は、設定では直らないので、ダイアログはそう伝え、利用者向けマニュアルの入れ直しの手順を開く。スイッチがサーバーを起動しない設定のとき（`speech_server_autostart_off`）は「ASRサーバー」を開く。どの場合も、その設定へ直接行ける。ほかの理由は通知のままとする。認識モデルがなく灰色になったスイッチも、機能のボタンから同じセットアップを開く。
- ローカルの Whisper（faster-whisper）エンジンは #288 で削除した。保存済みの`SELECTED_TRANSCRIPTION_ENGINE`が`"Whisper"`なら、読み込み時に1回だけローカル（speech.cpp）へ移し、移したことと必要なモデルを伝えるお知らせを1回出す（[保存形式](data-and-persistence.md#ローカル音声認識の移行)）。お知らせも移行も、モデルを取得しない。以前の版が取得した Whisper の重みは読まなくなり、利用者が設定で確かめて削除を選んだときだけ消す。
- 画面の変更によって、マイクの有効化、モデルの取得、メッセージの送信、音声経路の変更が勝手に起きてはならない（[契約](contracts.md)）。
- 利用状況の通知（テレメトリー）は既定でオンである。送るのは`app_started`（1日に1回）と`error`（エラーコードごとに1日に1回）の2種類だけで、送信した時刻（ISO 8601、UTC）、アプリのバージョン、OSの種類とバージョン、表示言語、PCの構成（CPUの名前と論理コア数、段階に丸めたメモリの量、GPUの名前・種類・ビデオメモリの量・ドライバのバージョン）が付く。「1日」はUTCの日付で数える。会話の文字と音声、音声デバイスやユーザーやPCの名前、パス、PCを見分ける番号は送らない。送る内容は`/get/data/telemetry_preview`でUIに渡し、お知らせの画面と設定で利用者に見せる。この応答は送信と同じ関数（`build_event`）で組み立てるので、送る内容と違うのは時刻だけである。送った内容は直近20件を`telemetry_state.json`に残し、設定で見せる。`error`に載るコードは`ErrorCode`と、音声まわりの失敗の一覧（`errors.REPORTED_FAILURES`）にあるものだけである。一覧にない失敗は機能ごとの`…_failed_other`にまとめるか送らない。`ErrorCode`のうち、失敗ではなく想定した状態に答えるコードは`ERROR_METADATA`で`"reported": False`にして送らない（いまは`TRANSLATION_MODEL_MISSING`だけ）。利用者がお知らせの画面で答えるまで（`TELEMETRY_NOTICE`がお知らせの現在のバージョンに達するまで）は、設定がオンでも送らない。前のバージョンの設定ファイルにある`ENABLE_TELEMETRY: false`は誰も選んでいない値なので、お知らせの答えで決め直す。送信を始められる答えは、お知らせの答え（`/set/data/telemetry_notice`）だけである（セキュリティ監査 SEC-07）。`/set/enable/telemetry`は設定の値を変えるだけで、お知らせに答えたことにはならず、未回答のあいだは何も送らない。設定画面のスイッチは、お知らせが未回答のあいだは、設定の値にかかわらずオフで表示する。実際に何も送っていないためである。下には、まだ選んでいないこと、いまは送っていないことを書き添える。このときスイッチを押すと、お知らせの答え（送る）を送る。設定画面にもお知らせと同じ送る内容が出ているためである。`/set/disable/telemetry`は答え（送らない）としても扱う。VRパネルからはどちらも中継しない（[VRパネルの中継](external-interfaces.md#tauriのコマンド)）。お知らせの「あとで決める」とEscapeは答えではない。その起動のあいだ画面を閉じるだけで、何も送らず、次の起動でもう一度出す。環境変数`VRCT_TELEMETRY=off`では、設定にかかわらず送らず、お知らせも出さない。実物のアプリを起動する試験はこの指定で起動する。送信の失敗は無視し、再送しない。本家のAptabaseのキーとSDKは使わない（[外部との接続](external-interfaces.md#利用状況の通知)）。
- アプリの更新はTauriのupdaterで行う（[アプリの更新](external-interfaces.md#アプリの更新)）。起動時の確認は`CHECK_SOFTWARE_UPDATES`（既定オン）で、バックエンドの初期化が終わってから1回だけ行う。利用者が更新のチャンネルを変えたときは、新しいチャンネルで確かめ直す（[アプリの更新](external-interfaces.md#アプリの更新)、#466、#1017）。送るのは最新版の問い合わせとダウンロードの要求だけで、会話、音声、設定は送らない。deb・rpmで入れたコピーと開発用のビルドは確認しない。確認や適用に失敗してもアプリは使い続けられ、適用の失敗では今の版のまま理由を表示する。Pythonの旧来の更新処理（`BUILTIN_UPDATER_ENABLED = False`）は使わない。バックエンドの更新のエンドポイントも同じupdaterを使い、起動時の確認（`/run/software_update_info`）は`CHECK_SOFTWARE_UPDATES`がオフなら通信しない。エラー画面の「新しいバージョンに更新する」のボタンは、新しい版があり、アプリの中で入れ替えられるコピー（`mode`が`install`）のときだけ出す。

## 秘密情報

- APIキーは`config.json`に書かず、OSの資格情報ストア（Windowsは資格情報マネージャー、LinuxはSecret Service）に保存する。0.5.xが`secrets.json`に保存したキーは、OSのストアに書いて読み戻せたものから移す。ストアが使えなくてもキーは黙って失わず、代わりに平文のファイルへ書くこともしない。アプリは鍵束を開くダイアログを出さない（[APIキーの保存先](data-and-persistence.md#apiキーの保存先)、[ADR-013](../adr/adr-013-secret-store.md)）。WebSocketのトークンはいまも`config.json`に平文で保存する。`config.json`の権限は0600である。WebSocketのトークンが不正な保存値なら新しい秘密値で修復し、空のトークンでサーバーを起動しない（[ネットワーク設定](data-and-persistence.md#ネットワーク設定)）。
- ログでは、名前に`auth_key`、`api_key`、`password`、`token`、`secret`、`voice_settings`、`instructions`を含む項目の値を`***MASKED***`にする。中核はこれに`client_id`、`user_model`、`translation_catalog`、`transcription_catalog`、`vocabulary`、`speaker_names`を足す（`native/core/src/log.rs`の`SENSITIVE_ENDPOINT_MARKERS`）。`vocabulary`はリアルタイム音声認識の設定にある用語辞書で、人や場所の名前を含むので伏せる（#446）。`speaker_names`は話者分離で見分けた声に利用者が付ける名前である（#447）。中核は要求の中の入れ子の項目も、応答と同じく項目名で判断して伏せる。会話の本文は診断ログに書かない。パスに含まれる利用者のホームフォルダーはOSのユーザー名を含むので、`~`に置き換えて書く。
- URLをログに書く前に、ユーザー情報とすべてのクエリ値を除く。プロバイダーの失敗は`errorLogging(provider=..., status=...)`で記録し、サービス名、例外クラス、取得できたHTTPステータス、発生位置のファイル名・行・関数名だけを残す。例外本文、原因となった例外の連鎖、ソース行は記録しない。SDKからの例外と、プロバイダーの呼び出し境界で印を付けた例外は、上位の共通処理に届いた場合も同じ扱いとする。
- ファイル操作や設定など、一般の`errorLogging()`は例外本文と連鎖を含むトレースバックを残す。ただし、保存済みのAPIキー・認証トークン・WebSocketトークンと一致する文字列、Bearerトークン、認証ヘッダー、キーを含むクエリやJSONの値を`***MASKED***`に置き換える。ログファイルに書けず標準出力へ出す場合も同じ処理を行う。例外から作るIPCエラーは、一般の例外なら同じ秘匿処理をした本文を含め、プロバイダーの例外ならクラス名だけを返す。
- 中核はLangChainとLangSmithを使わず、各APIを直接呼ぶ。ローカルのLLMを含め、会話をLangSmithへ送らない（0.4までのPythonは、`LANGSMITH_*`と`LANGCHAIN_*`の環境設定を除いてトレースを無効にしていた）。
- VRパネルからの要求は、APIキー、トークン、モデル取得、ファイルを開く操作、終了、更新を通さない（`src-ui/logics/common/vrPanelWire.ts`）。
- 設定画面のAPIキー欄は、保存済みのキーを「編集」の覆いで隠し、スペルチェックと自動補完を切る。

## 国際化

- 画面の文言はすべて`locales/`に置く。`en.yml`と`ja.yml`は必ず更新する。画面の言語は英語と日本語だけである。韓国語と中国語は0.1.0まで画面の言語として選べたが、0.2.0で外した。訳されていない文言が多く、英語で出る箇所が増えていたためである。保存済みの設定でどちらかを選んでいた場合は、英語で起動する。翻訳する言語としての韓国語と中国語はそのまま使える。
- ページの言語（`<html lang>`）はUIの言語に合わせる。
- UIの言語を変えても、画面を作り直さない。開いている設定のページ、開いた折りたたみ、入力の途中の文、フォーカスはそのまま残り、文言だけが新しい言語になる。VRパネルの設定から変えたときも同じである（#904）。
- サイドカーの`message`は英語の既定文である。画面ではエラーコードから引いた文言を出す。
- 言語や国の組は中核の言語の表（`native/core/data/transcription_languages.json`）にあるものだけを受け付ける。

言語名と国・地域名の表示・検索:

- メイン画面、設定、VRパネルの表示名とアクセシブル名は、現在のi18nextのUI言語を指定した`Intl.DisplayNames`で求める。言語のタグは`Intl.Locale`で言語・文字体系・地域に分ける。文字体系を残して中国語の簡体字・繁体字を区別する。UI言語を切り替えたら表示も更新する。
- タグの正本は`native/core/data/transcription_languages.json`の`Google`列。`python tools/language_codes.py --write`がUI用の`src-ui/logics/common/languageCodes.ts`を生成し、toolingチェックが差分を検出する。モデルの選択で候補から外れた保存済みの言語やOCRの旧設定にも、この表を使う。リアルタイムASRとUI言語の選択肢は、もともと持っている言語タグを使う。
- タグがない、タグが不正、またはプラットフォームが表示名を返せない場合は元の英語名に戻す。言語と地域のフォールバックは独立している。
- メインとVRの言語一覧は`Intl.Collator`で表示名順に並べる。検索はUI言語と英語の言語名・地域名を対象にし、大文字小文字と全角・半角を区別しない。Enterで表示中の先頭候補を選ぶが、IMEの変換確定中は選ばない。VRでは先頭候補が選択済み・利用不可なら変更しない。
- VRの言語一覧は2列を保ち、検索前の候補が50件以上なら画面周辺の行だけを描画する。選択済みの候補は一覧を開いたときに表示し、検索すると先頭へ戻す。画面外の候補にも頭文字のボタンやTabで移動でき、処理中や利用不可の候補は従来どおり選べない。並べ替えは候補かUI言語が変わったときだけ行い、検索ではその結果を絞り込む。
- VRの「すべての言語から選ぶ」には、表示中の言語名の頭文字から先頭候補へスクロールするボタンを置く。日本語はア・カ・サ・タ・ナ・ハ・マ・ヤ・ラ・ワの行と「その他」（漢字や別の文字体系）、英語はA〜Z、韓国語はハングルの初声を使い、候補のあるグループだけ表示する。日本語の濁音・半濁音、小書き、ひらがな、半角カナは元の行にまとめ、先頭の長音符は飛ばす。ンはワ行に含める。英語と韓国語にも分類できない名前の「その他」がある。中国語（繁体字・簡体字）と未対応のUI言語にはジャンプを置かない。読みや画数を推測せず、一覧と検索を使う。ボタンは並び順や選択値を変えず、絞り込みとUI言語の変更に追従する。デスクトップの言語一覧には追加しない。
- 設定検索もOCR、UI言語、取得済みのリアルタイムASRモデルの言語名をUI言語と英語で検索する。UI言語の選択肢には、その言語の自称も併記する。
- 保存・IPC・OSC・プリセットの英語の識別子は変えない（[データ形式と保存](data-and-persistence.md#言語の組タブごと)）。

## 停止とミュート

- 「読み上げを停止」（`/run/stop_voice`）は読み上げだけを止める。待ち行列を空にし、話している途中の音声も止める。読み上げのオン・オフとミュートの状態は変えない。
- 「ミュート」（`/run/mute_voice`）は音声経路を止める。管理対象の経路（Linuxの仮想マイク）では、読み上げとRVCの変換音声の両方を止める。Windowsでは出力デバイスの手前で両方を無音に置き換える。OSの遮断がないので、音声の流れは止めない。マイクの読み上げで直接音声を抑える設定も、Windowsでは同じ方法で変換音声を無音にする。読み上げと変換音声のスピーカーモニターも無音にし、モニターで再生を待っている音声は捨てる。ミュート中に変換を開始してもモニターは鳴らさない。ミュートの状態は`voice_mute_state.json`に保存し、再起動しても続く。
- 「読み上げを声の変換に通す」（`VoiceSettings.conversion`）をオンにすると、声の変換が動いているあいだ、読み上げは出力デバイスへ出さずに変換の入力へ送る。読み上げのあいだはマイクの代わりに読み上げを変換し、終わるとマイクに戻る（[ADR-007](../adr/adr-007-translated-speech-through-voice-conversion.md)）。ミュートは変換した読み上げも止める。マイクの読み上げで直接音声を抑える設定は、このときマイク由来のブロックだけを無音にし、変換した読み上げは出す。Linuxでは、このときの抑制はOSのゲートで確かめたものではなく、変換のプロセスが行う。「直接音声と読み上げを混ぜる」とは一緒に使えない。声の変換が動いていなければ、読み上げはこれまでどおり出力デバイスへ出す。
- 変換ワーカーとTTS・RVCのオンオフは、ミュートや解除で変えない。既存の再開確認が済むまでモニターもミュートを保ち、解除後に取り込んだ新しい変換音声だけをモニターへ流す。ワーカーへのミュート通知が失敗した場合は、既存の`vc_router_failed`または`vc_router_timeout`で知らせ、故障時の終了処理でモニターを閉じる。
- Linuxの外部の経路では読み上げだけを止める。外部アプリの変換音声や経路は制御しない。Linuxのアプリ内の変換音声とそのモニターは管理対象の経路でのみ開始できるため、外部の経路に変換音声モニターの例外はない。Windowsのアプリ内の変換音声は出力デバイスへ流れ、上のとおりミュートの対象になる。
- 読み上げ停止とミュートは、モデルカタログの試聴（[UC-19](use-cases.md#uc-19-読み上げの声を試聴する)、[UC-20](use-cases.md#uc-20-ボイスチェンジャーの声を試聴する)）も止める。ミュート中は試聴を始めない。
- 読み上げ（TTS）とRVCは別のスイッチで、片方の操作がもう片方を止めない。
- `VOICE_SETTINGS.mic_mode` は、マイクのリアルタイム認識の確定発話をどう読み上げるかを選ぶ。値は `off`（読み上げない）、`original`（原文を発話言語で読む）、`translated`（翻訳がオンで、選んだ枠の翻訳が成功したときに訳文を読む）。`original` と `translated` には、同じ出力先・音声経路・直接音声の設定（`direct_policy`）を使う。
- メイン画面の機能スイッチはEnter・Spaceのキーリピートを無視する。停止の応答が届いた後も、同じ押し続けたキーで再びオンにしない。TTS・RVCの開始待ちを取り消すには、新たにキーを押すかクリックする。
- 停止の要求はキューを通らず、すぐに処理する（[IPCプロトコル](ipc-protocol.md#並行性とロック)）。
- 停止すると世代番号が進む。止める前にキューに入っていたメッセージは、送信や記録はされるが、古い世代の音声は鳴らさない。
- リアルタイム認識の確定結果には、セッションの受信キューに入る前に音声の世代番号を付け、字幕の通知や翻訳を待つ間も保持する。読み上げ停止、音声ミュート・再開、TTSのオフ・オンを挟んでも、待っていた結果を新しい世代の音声として読み上げない。テキストの配送は続ける。
- VRCマイクミュート同期がオンで、VRChatのミュートを受け取ったときや状態の再確認を始めるときは、マイク結果の配送世代を進める。翻訳・描画・キュー待ちの結果は、解除後も配送しない。従来の文字起こしも推論開始時の配送世代を結果のバッチ全体で保ち、途中で失効したら残りの結果を捨てる。ミュート中に受け取った字幕・確定結果も捨てる。スピーカー、OCR、入力欄・Quick Chatの結果には影響しない。
- マイク・スピーカーの文字起こしとOCRを利用者がオフにしたとき、またはエラーで機能を無効にしたときは、その入力元の配送世代を後始末の待機より先に進める。終了時は後始末を待つ前に全入力元の配送を失効させ、新しいメッセージの受付も閉じる。以後、世代を進めても受付は再開しない。終了への応答と必要な完了通知は維持する。各出力直前に世代を確かめ、遅れて戻った結果をOSC、オーバーレイ、WebSocket・OBS、会話ログ、UI・VRの行や字幕、クリップボード、読み上げへ新たに配送しない。再開しても古い結果は復活しない。失効した描画の未公開履歴も破棄し、後続の表示に混ざらないようにする。既に配送した内容は取り消さず、後始末の待機上限と終了時のガードも維持する。
- デバイス一覧の更新、設定画面での一時停止、従来の文字起こしからリアルタイム認識への切り替えでは、配送世代を進めない。受付済みの従来の文字起こし結果は配送を続ける。設定画面は文字起こしの disable エンドポイントに `{"reason":"settings_pause"}` を渡し、利用者のオフと区別する。設定画面を閉じて元へ戻すときは、enable エンドポイントに `{"reason":"settings_resume"}` を渡す。一時停止の間に利用者が内蔵の音声認識サーバーを止めていた場合、そのサーバーを使う入力の復帰は断り、`200` と偽を返してスイッチをオフのままにする。設定画面を閉じただけでは、止めたサーバーを起動し直さない。利用者がメイン画面でスイッチを押した場合は、理由を付けずに届くので断らない。デバイス消失も、代替デバイスへの切り替えでは失効させず、代替がなく文字起こしを無効にする場合に失効させる。リアルタイム認識の既存のセッション世代と鮮度制限は引き続き適用する。

## 初期化中、オフライン、能力の不足

- 初期化が終わるまで、翻訳・音声認識のオンオフやメッセージ送信は423で待たせる。UIは起動直後からメイン画面を出すが、`IsBackendReady`が真になるまで`inert`にして操作させず、`aria-busy`と画面外のライブリージョンで起動中であることを支援技術にも伝える。サイドカーから届いていない値は同じ大きさの仮の表示（スケルトン）にし、準備が整った時点で配置を変えずに実際の値へ替える。仮の表示の動きは控えめにし、`prefers-reduced-motion`では止める。設定画面、同意のダイアログ、ウィンドウの位置と大きさの保存は準備が整ってから始める。
- メインウィンドウは非表示で作る。アプリは`config.json`から保存した位置と大きさを読み、ウィンドウに当ててから表示する（`src-tauri/src/window_placement.rs`）。表示したあとに位置を動かさない。保存がないとき（初期値のとき）は、ウィンドウがあるモニターの作業領域の中央に置く。大きさは CSS ピクセルで 870×654 とする。保存した位置がどのモニターにもないときは、ウィンドウがあるモニターの中に収める。
- 初期化の一部の項目が取得・反映できなくても、残りを反映して警告とともに画面を開く。サイドカー自体の起動に失敗した場合は、操作できないメイン画面の上に失敗のダイアログを出し、理由（起動できなかったか、準備の途中で終了したか）、次の行動、手動の再試行と終了のボタンを示す。既定値の扱い、セッションの所有者、再試行の条件は[起動と初期化](ipc-protocol.md#起動と初期化)に従う。
- いま選んでいるエンジンが必要とする内蔵モデルがないときは`/run/enable_ai_models`が偽になる。UIはこのとき通知を出さない。対象は、選択中のタブの翻訳エンジンがCTranslate2で翻訳モデルがない場合だけである（`Controller._missingBuiltInModelInUse`）。選んでいないエンジンのモデルがないだけでは偽にしない。テキストチャットと外部の音声エンジンは使える。
- 足りないものは、会話が空のあいだ、それを用意する入口と一緒に会話欄へ表示する（UIが持つモデルの一覧と音声サーバーの設定から判定する。`src-ui/logics/main/setupNeeds.ts`）。翻訳エンジンがCTranslate2で翻訳モデルがなければ、そのモデルを取得できるとき（ダウンロードのカタログに、選んでいるモデルの項目があるとき）は取得の確認画面を開くボタンを、取得できないときは翻訳エンジンの一覧を開くボタンを出す。音声認識エンジンがローカル（speech.cpp）で、リアルタイム音声認識のサーバーが同梱、音声サーバーの`asr`プロファイルに認識モデルか VAD モデルがなければ、設定の「音声認識（ASR）」を開くボタンを出す。ここからは取得しない。
- 翻訳のスイッチを押したときに翻訳モデルがなければ（`TRANSLATION_MODEL_MISSING`）、通知の代わりに、その場で取得の確認画面を開く（`src-ui/views/app/_app_controllers/TranslationSetupController.tsx`）。そこでカタログの翻訳モデルのうち、選んでいるモデルの種類のどれかを取得すると、検証が終わったところでアプリが適用し、中核がモデルを取得済みとしたら翻訳をオンにする（#1015）。翻訳のモデルの適用は設定を書かない。取得が失敗したか取り消されたとき、確認画面に並ぶほかのモデルを取得したとき、会話欄の入口から開いたときは、オンにしない。モデルの選択とマイクのオン／オフは変えない。
- メイン画面の機能のスイッチは、前提が足りない間は非活性にする（`src-ui/logics/main/switchBlocks.ts`）。マウスを重ねたときと、キーボードのフォーカスが来たときに、ツールチップに理由と用意する場所が出る。スクリーンリーダーには同じ文をスイッチの説明として読ませる。前提は、上の判定と、設定がすでに持っている状態から取る。翻訳はCTranslate2のモデルがない（取得中も含む）、マイク入力と聞き取りはローカルの音声認識のモデルがない、チャット読み取りは選んだ言語に対応していないか、その言語のモデルがない（`/get/data/ocr_model_readiness`。ファイルの有無だけを見て、ウィンドウは探さない。起動時の設定に含める。チャットボックス検出器のモデルの有無と、使う設定かどうかも含め、設定のチャット読み取りのページは、自分の問い合わせの答えが来る前からこれでモデルの一覧と検出器の欄を描く）、テキスト読み上げは読み上げる内容がどちらもOFFか、管理対象の経路でないのに出力デバイスを選んでいないか、どの声もモデルを持たないとき（足りないものはTTSのページの順にまとめて挙げ、アイコンは最初のものへ案内する。#1314）、ボイスチェンジャーは保存したモデルと実行環境がないか音声経路が整っていない、のときに非活性にする。まだ届いていない状態では非活性にしない。前提がそろえば、再起動しなくても活性に戻る。
- 前提が足りなくて灰色のスイッチを押すと、まだオンにできない理由と、「閉じる」と下のアイコンのボタンと同じ直し方のボタンを持つダイアログを開く（#1314。音声認識のスイッチのダイアログと同じ形、#1225）。何もオンにしない。ほかの理由で使えないスイッチ（エンジンがない、切り替え中）は押しても何もしない。アイコンだけの細い表示でないときは、各機能の左のアイコンをボタンにし、スイッチとは別の要素として並べる。アイコンのボタンは前提が足りないときは用意する場所を開き、足りているときはその機能の設定を開く。翻訳は選んでいるモデルを取得できるときは取得の確認画面を、それ以外は翻訳エンジンの一覧を開く。マイク入力と聞き取りは「音声認識（ASR）」、ほかは同じ名前の設定のページを開く。ボタンの名前とツールチップには行き先を書く。前提の判定が届いても行の構成と大きさは変えず、スイッチの下にボタンを足さない。ここからは取得もオンもしない。オンのスイッチやオンに切り替えている途中のスイッチは、前提がなくなっても非活性にしない。オフにできるようにするためである。前提がなくなったことは、これまでどおりスイッチのエラーと案内で知らせる。ホットキーからの操作は、この判定を通さない。
- 判定はメイン画面で1回だけ行い、結果を`SwitchBlocks`のatomに置く（`SwitchBlocksController`）。中身はスイッチごとの理由と行き先の識別子だけで、利用者のデータは入らない。メイン画面のスイッチとVRパネルのランチャーは、どちらもこのatomを読む。オンのスイッチと切り替え中のスイッチを除く規則も共通（`activeSwitchBlock`）。
- VRパネルのランチャーの5つのスイッチ（翻訳、マイク入力、聞き取り、チャット読み取り、テキスト読み上げ）も、同じ条件で非活性にする。読み上げのスイッチとその横の停止は、メイン画面の読み上げのスイッチと上のバーの停止を押す（`vr-panel-voice`、#1314）。停止は非活性にしない。ボタンは灰色にして注意の印を付け、押しても何もしない。理由と、PCの設定のどこで用意するかは、ボタンの吹き出しに出す。VRには理由を読める場所がほかにないので、この吹き出しは操作の吹き出しをOFFにしていても出す。VRからは設定のページを開かない。設定のページを開いている間のロック（ブラウザーのとき。設定のウィンドウでは何もロックしない。#1236）は、前提の不足より先に示す。前提がそろえば、再起動しなくても活性に戻る。
- 起動時に確かめるのは、使っているエンジンだけにする（#457）。翻訳はどれかのタブで選んでいるエンジンと、外へ出ずに確かめられるエンジン（CTranslate2と、アドレスがループバックのLM Studio、Ollama、OpenAI互換）、音声認識は選んでいるエンジンと、アドレスがループバックのカスタムWhisperである。ループバックは`localhost`、`127.0.0.0/8`、`::1`。確認はエンジンごとのスレッドで並べて行う（`native/core/src/controller/translation.rs`、`transcription.rs`）。それ以外のエンジンには起動時に接続しない。キー（OpenAI互換とカスタムWhisperはURLも、PapagoはClient IDも）を保存していれば選べる状態にしておき、選んだとき（翻訳は`/set/data/selected_translation_engines`、音声認識は`/set/data/selected_transcription_engine`）か、翻訳で初めて使うときに確かめる。モデルの一覧はそのときに取る。すでに使えない状態のクラウドのエンジンは、選んだときにも確かめ直さない。LAN上のLM StudioとOllamaはキーがなく、モデルの一覧がないと使えないので、選んでいなければ設定画面の接続の確認を押すまで使えない状態になる。
- CTranslate2は、設定に残るローカル翻訳のエンジンの名前である。中身はONNX RuntimeのM2M100とNLLB-200で（`native/translate-onnx`）、既定のモデルは`m2m100_418M-ct2-int8`の名前で選ぶ。
- 起動時と選んだときにAPIキーを確かめ、確かめられなかったエンジンは使えない状態にする。キーは消さない。確認の失敗は、キーの拒否のほかに、オフライン、タイムアウト、429、5xxでも起きるからである。使えなくなったエンジンを選んでいたタブはCTranslate2に戻し、UIには`/run/selected_translation_engines`と`/run/translation_engines`で新しい選択と一覧を送る。確認の失敗そのものは通知しない。音声認識のエンジンは選択を変えず、そのエンジンのモデルの一覧、選んでいたモデル、Deepgramの言語を消す（`native/core/src/controller/lifecycle.rs`の`forget_failed_engine`、[同意と外部への送信](#同意と外部への送信)）。
- 起動時のエンジン確認に、段階ごとの期限はない。翻訳の確認、続いて音声認識の確認が、それぞれすべてのスレッドが終わるまで待つ。1つの確認の長さは、下の通信の待ち時間で決まる。起動全体には180秒の期限がある（`native/core/src/backend.rs`の`STARTUP_LIMIT`）。過ぎると中核はログに記録して終了コード124で終わり、確認のあとに始めたものを止め、エンドポイントを開かない。0.4までのPythonは、確認の段階ごとに30秒で打ち切っていた（[`controller.py`](https://github.com/kein5/astarot/blob/v0.5.2/src-python/controller.py)の`_runEngineChecks`）。
- キーの確認とモデルの一覧の取得は、接続、読み取り、書き込みの待ちをそれぞれ3秒にし、再試行しない（翻訳は`native/translation/src/providers/mod.rs`の`DISCOVERY`、音声認識は`native/transcription/src/providers.rs`の`DISCOVERY`）。LM StudioとOllamaが動いているかの確認は0.2秒（`LOCAL_PROBE`）、Ollamaのモデルの一覧（`/api/tags`）は2秒（`OLLAMA_TAGS`）で待つ。Geminiのモデルの一覧は、ページ送りを含めて全体を8秒（`DISCOVERY_DEADLINE`）で打ち切る。各ページの待ちを残りの時間に縮め、期限のあとは次のページを取りに行かない。ほかの確認に全体の期限はなく、要求を2回送るOpenRouter（`/auth/key`と`/models`）とDeepgram（キーとモデル）は、それぞれ最大3秒ずつ待つ。起動時と設定画面からの確認は同じ待ち時間である。
- 中核は各社のSDKを使わず、要求ごとに接続を開いて閉じる（`Connection: close`、`native/translation/src/http.rs`）。閉じる通信クライアントや接続プールはない。OSのDNS解決には待ちの上限がない。
- 実行時のネットワーク翻訳の待ち時間（接続、読み取り、書き込み。読み取りは1回の読み取りごと）は次のとおり（`native/translation/src/providers/mod.rs`）。
    - OpenAI、OpenAI互換（クラウド）、OpenRouter、Groq、Plamo: 5秒、30秒、10秒（`CLOUD_CHAT`）
    - OllamaとLM Studio、アドレスがローカルかLANのOpenAI互換: 5秒、120秒、10秒（`LOCAL_CHAT`。初回のモデルの読み込みを待つため）
    - Gemini: それぞれ30秒
    - DeepL、Google Cloud Translation、Papago: 5秒、10秒、10秒（`MACHINE_TRANSLATION`）
- 上流VRCTのGoogle・Bing・PapagoのWeb翻訳は、ASTAROTでは配布できないので翻訳エンジンの一覧に出さない（`native/core/src/languages.rs`の`RETIRED_WEB_TRANSLATORS`）。
- クラウドの翻訳は、一時的なエラーのときに1回だけ再試行する（初回を含め最大2回。`native/translation/src/providers/mod.rs`の`Api::attempt`）。認証の拒否など再試行しないエラーは、そのまま失敗にする。OllamaとLM Studio、ローカルかLANのOpenAI互換は再試行しない。失敗が続いた場合は、タイムアウトもほかの翻訳の失敗と同じく、CTranslate2での訳し直しに進む。
    - 判定と待ちは、0.4までのPythonが使っていた各SDKの規則を`native/translation/src/providers/retry.rs`に写したものである。OpenAIのSDKの規則（408・409・429・5xxと通信の失敗、`x-should-retry`、`retry-after-ms`と`retry-after`。サーバーの指定は120秒までなら待ち、超えれば再試行しない。指定がなければ0.375〜0.5秒）、DeepLのSDKの規則（429と5xxと通信の失敗。2回目は1回目を始めてから1秒後）、GoogleのSDKの規則（Gemini。408・429・500・502・503・504と通信の失敗。待ちは1〜2秒で、サーバーの指定は使わない）である。中核で足したGoogle Cloud TranslationとPapagoはOpenAIのSDKの規則に従う。
    - 判定、待ち時間、バックオフが0.4までのPythonのクライアント（各SDK）と同じであることは、`native/translation/tests/contract/providers.json`の契約テストで確かめる。ローカルかLANのOpenAI互換に`LOCAL_CHAT`を使い再試行しないことだけは、意図した違いとして記録している（`local-openai-compatible`）。
    - 温度を指定していて、チャットのプロバイダーが400を返したときは、`temperature`を外して送り直す（`native/translation/src/providers/chat.rs`）。送り直しにも再試行があるので、1つの翻訳の要求は最大3回（400に`x-should-retry: true`が付けば4回）になる。
- Ollamaとチャットのプロバイダーには、非ストリーミング（`"stream": false`）を明示する。タイムアウトのために呼び出しごとのスレッドを作らない。翻訳の要求は呼び出したスレッドで接続し、接続と読み書きの待ちはソケットの設定で制限する。DeepLのキーの確認は`DISCOVERY`の1回の要求で、翻訳は`MACHINE_TRANSLATION`で送る。
- これらは通信の待ちの制限であり、翻訳全体の経過時間の上限ではない。少しずつデータが届き続ける場合、DNS解決、CTranslate2のロックの待ちとローカルの推論、再試行の前の待ちは中断できない。失敗のログに残すのはエンジンの名前までで、エラーそのものは書かない（`native/core/src/controller/translation.rs`）。プロバイダーのエラーは決まったコードで、キー、URL、要求の本文を含まない。

フォールバックに進むまでの待ち時間の目安は下表のとおり。各試行で接続と読み取りの待ちがそれぞれ1回あると仮定し、`(接続 + 読み取り) × 試行回数 + 再試行の前の待ち`で保守的に積み上げる。書き込みの待ちも各1回加えた値を併記する。DNS、通信が進み続ける場合、処理の時間、`temperature`を外した送り直し、CTranslate2での訳し直し（ローカルのモデルを読み込んでいる間は、100ミリ秒おきに20回まで繰り返す）は含まないので、翻訳全体の経過時間の保証ではない。

| プロバイダー | 最大試行回数と再試行の前の待ち | 接続＋読み取りの待ちの目安 | 書き込みの待ちも含めた目安 |
|---|---|---|---|
| OpenAI、OpenAI互換（クラウド）、OpenRouter、Groq、Plamo | 2回。通常は0.375〜0.5秒。サーバーの`retry-after-ms`や`retry-after`の指定を120秒まで使う | 通常は`(5 + 30) × 2 + 0.5`で約70.5秒。サーバーの指定を含めると最大約190秒 | 通常は約90.5秒。サーバーの指定を含めると最大約210秒 |
| Google Cloud Translation、Papago | 2回。待ちはOpenAIの規則と同じ | 通常は`(5 + 10) × 2 + 0.5`で約30.5秒。サーバーの指定を含めると最大約150秒 | 通常は約50.5秒。サーバーの指定を含めると最大約170秒 |
| Gemini | 2回。1〜2秒。サーバーの指定は使わない | `(30 + 30) × 2 + 2`で約122秒 | 約182秒 |
| DeepL | 2回。最初の要求を始めてから1秒までの残り（0〜1秒） | `(5 + 10) × 2 + 1`で約31秒。最初の要求が1秒以上かかれば待ちは0秒 | 約51秒 |
| Ollama、LM Studio、ローカルかLANのOpenAI互換 | 1回。待ちなし | `5 + 120`で約125秒 | 約135秒 |

- 翻訳に失敗したときはCTranslate2で訳し直す。空でない原文への空の訳も失敗として扱う。LLMの応答が長さの上限で切れた場合（OpenAI互換の`finish_reason: length`、OpenAI Responses APIの`incomplete_details.reason: max_output_tokens`、Geminiの`finish_reason: MAX_TOKENS`、Ollamaの`done_reason: length`）は途中の訳を捨て、空の訳と同じ処理に進む。終了理由が返らない場合は、本文の長さから打ち切りを推測しない。
- CTranslate2では、特殊トークンを含む入力が1,024トークンを超えたら推論せず失敗として扱う。入力の自動切り詰めを無効にし、出力の生成上限は256トークンに固定する。結果に終了トークンがなければ途中の訳を捨て、既存の翻訳失敗処理に進む。終了トークンは訳文に含めない。
- CTranslate2で訳し直せた場合は、その訳を使い、失敗の通知は出さない。訳し直せなかった場合は原文を使い、失敗として返す。呼び出し元はエンジンをCTranslate2へ切り替え、`/run/error_translation_engine`に既存の`TRANSLATION_ENGINE_LIMIT`を送る。両方のエンジンが言語ペアに未対応なだけの場合は、原文を使って成功として扱い、通知しない（`Model.getTranslate`、`Controller._processMessage`）。
- 複数の翻訳先へ同時に訳すとき、ある翻訳先のスレッドが異常終了したら（中核の panic）、その翻訳先は訳し直せなかった場合と同じく原文を使い、失敗として扱う。ほかの翻訳先の訳はそのまま使う。GPU のメモリー不足として扱わず、翻訳はオフにしない。メモリー不足の経路（`TRANSLATION_VRAM_*`と`TRANSLATION_DISABLED_VRAM`）に進むのは、エンジンがメモリー不足を返したときだけである。
- 訳文読み上げは、選んだ枠に空でない実際の訳文があるときだけ行う。翻訳結果には枠ごとの成功フラグと由来（`translated`、`failed`、`unsupported`）を持たせる。失敗時の原文も、未対応ペアで成功扱いにした原文も読み上げない。原文と同じ文字列でも、翻訳器が成功として返した訳なら読み上げられる。テキストのフォールバックと失敗通知は上記のまま。
- OSCQueryのcapabilityは受信と広告の準備結果から決める。使えなくなったとき、同期がオンだったマイク入力を自動で再開しない。状態が不明な間の一時停止、失敗時の入力停止、設定の復旧、通知の詳細は[OSCの契約](external-interfaces.md#vrchatへのosc)に従う。

## ホットキーと設定画面

- 設定のウィンドウがホットキーのページを出している間は、すべてのホットキーを無効にする。キーの入力中に機能が動かないためである。設定のウィンドウのほかのページでは、何も止めない（#1236、2026-11-26 の決定）。設定がページになるブラウザーでは、開いている間は無効にする。
- ホットキーの登録は`GlobalHotKeyController`が一括して管理する。バックエンドの準備、更新中かどうか、設定のページの開閉、設定のウィンドウがホットキーのページを出しているかどうかに加え、保存応答で確認したホットキーの内容を監視する。設定画面を閉じた後に保存応答が届いても、古いキーを解除して新しい内容を登録する。削除したキーも解除する。古い非同期登録の完了やコールバックでは新しい状態を戻さない。
- ホットキーの変更・削除は、編集した操作のキーだけを送る。ネイティブの競合確認を待つ間も編集内容を保持し、確認済みのキーと応答待ちのキーの両方で重複を調べる。確認が終わった時点でも最新の内容を調べ、同じ操作への古い編集は送らない。
- ホットキー欄ではTab／Shift+Tabでフォーカスを移動し、Escapeで入力途中の組み合わせを取り消して保存済みの表示に戻す。これらのキーは保存しない。フォーカスが外れた場合も入力途中の組み合わせを取り消す。ほかのキーの組み合わせはキーを離したときに保存する。
- Waylandではデスクトップのショートカット機能（GlobalShortcuts portal）で登録する。それ以外ではTauriのグローバルショートカットを使う（[外部インターフェース](external-interfaces.md#ホットキー)）。

## 用途別プリセット

- 設定のメニューの最上部の「用途」で、使い方に合わせて表示する機能を絞る（#554）。用途は複数を選べ、どれかの用途が出すものを出す（和集合）。どれも選んでいない状態にはできない。
- 用途は表示だけを決める。機能のオン・オフ、デバイス、音声経路、モデルは変えず、マイクも開かない。
- 用途と表示するもの（メイン画面のスイッチ、設定のメニューのページ）の対応は、UIの`src-ui/logics/configs/usagePresets.ts`の1か所にある。デザイン、ホットキー、アップデート、高度な設定、実験的機能、ASTAROTについては、どの用途でも出す。
- オンのスイッチと、オンとオフを切り替えている途中のスイッチは、用途に関係なく出す。止める手段が隠れることはない。初期設定が準備した機能のスイッチも、オンにされるまで目立たせている間は出す（[UC-18](use-cases.md#uc-18-初期設定で基本機能を準備する)）。用途で隠したスイッチは、スイッチの列の下の「ほかの機能（件数）」で出せる。出したかどうかは保存せず、設定も変えない。ホットキーとVRパネルとトレイのパネルは、隠したスイッチも今までどおり切り替える。
- 隠したページも設定の検索で見つかる。検索やメイン画面のボタンで開いたページは、開いている間はメニューに出す。ページの中の項目は、用途に関係なくすべて出す。
- 保存は`USAGE_PRESETS`（[データ形式と保存](data-and-persistence.md#その他)）。値がまだ届いていないときと、読めない値のときは、何も隠さない。新しく入れたときは「基本」、前の版から更新したときは「すべて表示」で始まる。
- 用途の名前は仮のもので、利用者に試してもらって決める（#554 の Q-14）。

## 実験的機能

- experimentalブランチで試作し、実機の確認を通った機能は、通常の設定へ卒業するまで設定の「実験的機能」ページに置く（Issue #361）。どれも既定はオフで、利用者がページのスイッチでオンにしたときだけ動く。
- 機能に属するコードはオンのときだけ通る。UIは`useExperimentalFeature(id)`、バックエンドは`experimental_features.is_enabled(config.EXPERIMENTAL_FEATURES, id)`で確かめる。どちらも一覧にない機能やまだ確認できていない値はオフとして扱う。
- スイッチはその機能の値だけを`/set/data/experimental_features`で送り、応答で確認した値を表示する。保存は即時で、形は[データ形式と保存](data-and-persistence.md#その他)にある。
- 項目がないときは、試せる機能がないことをページに出す。VRパネルからは変えられない（中継を許す一覧に載せていない）。
- VRパネル（VR UI）も試験中の機能として、このページに並べる（#554 の Q-05）。ただし`EXPERIMENTAL_FEATURES`の辞書には入れず、前からの保存値`OVERLAY_VR_PANEL`と`/set/enable/overlay_vr_panel`・`/set/disable/overlay_vr_panel`をそのまま使う。保存の形が変わらないので、オンにしていた人はオンのまま引き継ぐ。ランチャーの位置を戻す操作は、VRパネルがオンの間だけその下に出す。「字幕とVR」のページには、ここへ移る行だけを置く。

### トレイアイコン

- 0.5.0 から、アプリは起動するとシステムトレイにアイコンを1つ置く。実験的機能のオン・オフに関係なく出し、六芒星のオーバーレイもこの1つを使う（別のアイコンは置かない）。
- メニューはメイン画面を開く、「マイク入力」（マイクの音声認識のメインのスイッチ）をオンとオフにする、ASTAROTのコントロールパネルを開く、六芒星を出すモニター、終了。どの項目も、アプリを開かずに読んで何をするか分かるようにする（#1234）。オンとオフの項目は切り替えるメインのスイッチの名前を、コントロールパネルはASTAROTのもの（システムのコントロールパネルではない）であることを、モニターは実験的機能のページの設定と同じ言葉を使う。コントロールパネルと表示するモニターは、六芒星のオーバーレイがオンの間だけ使え、オフの間は灰色で出す。文言はメイン画面が表示言語で送る。終了はメイン画面の閉じるボタンと同じシャットダウン（設定の保存）を通る。
- 左クリックは、六芒星のオーバーレイがオンならコントロールパネルを開閉し、オフならメイン画面を出す。
- アプリはトレイに常駐する。メイン画面の閉じるボタン（Alt+F4 なども）では終了せず、トレイにしまう。終了はトレイのメニューの「終了」から行う。実験的機能のオン・オフに関係ない。しまってある間にメイン画面がダイアログを開いたとき（認識の同意など）と起動に失敗したときは、メイン画面を前に出す。トレイや六芒星、そのパネルで切り替えた機能が使えないときも前に出す。メイン画面のスイッチが理由を示して押せなくしている機能は、切り替えずに理由を通知する。バックエンドが拒否したときは、切り替えから30秒以内に出たエラーの通知を拒否の答えとみなす。
- トレイを作れない環境（Linux でトレイ用のライブラリがないときなど）では、アイコンなしで動き、閉じるボタンでこれまでどおり終了する（しまうと戻せないため）。Linux ではライブラリを読み込めるかを先に確かめ、読み込めなければトレイを作らずに起動する。アイコンを作れても表示する場所がない Linux のデスクトップ（AppIndicator の拡張機能がない GNOME など）も同じ扱いにする。閉じるたびに、セッションバスに StatusNotifierWatcher がいるかを確かめ、いなければ終了する。エラー画面と起動失敗の画面の「閉じる」「終了」も、トレイにしまわずに終了する。

### 六芒星のオーバーレイ（`tray_companion`）

- オンの間は、メイン画面を出さずにトレイで起動できる。メイン画面はそのまま作られ、バックエンドの起動とデスクトップ字幕の駆動を続ける。動作確認の方法が決まっていないため、この機能は experimental ブランチでの実機の確認を経ずに、既定オフの実験的機能として載せた。
- 起動時は、Rust 側がバックエンドと同じ規則で求めた設定フォルダの`config.json`を読む。`EXPERIMENTAL_FEATURES.tray_companion`が`true`ならメイン画面を出さずにトレイで始める。読めない、壊れている、`true`でないときは通常どおり起動する。起動したあとは、メイン画面が設定の値に合わせて`companion_set`で切り替える。
- コントロールパネルは状態（起動中、停止中、認識中）、メイン画面の機能のスイッチ、メイン画面を開くボタンを持つ。Esc、閉じるボタン、フォーカスが外れたときに閉じる。スイッチはメイン画面の既存の切り替えを呼ぶだけで、同意や確認の流れは変わらない。
- パネルのスイッチは、メイン画面と同じ6つを、メイン画面の順と名前で並べる。翻訳、マイク入力、聞き取り、チャット読み取り（OCR）、テキスト読み上げ（TTS）、ボイスチェンジャー（RVC）である（#1235）。状態はメイン画面が持ち、変わるたびに知らせるので、どちらで変えても両方にそろう。メイン画面がオンにできないスイッチは、黙って失敗しない。メインのスイッチが灰色のものは、パネルでもそう表示し、押すと理由と一緒にメイン画面を出す。エンジンが断ったときはエラーの知らせになり、メイン画面を出す。スイッチが開くダイアログ（同意、モデルの準備）もメイン画面を出す。六芒星の札と同じ扱いである。メイン画面のスイッチの一覧は試験が読むので、メイン画面にスイッチを足してパネルに足さないと、その試験が落ちる。
- オンの間は、保存された設定を変えずにデスクトップ字幕を表示する。
- 六芒星の魔法陣（ASTAROT のシンボルの形）を画面の端に隠しておき、そこから操作する。どの端に隠すかは設定の`TRAY_COMPANION_EDGE`（右、左、上、下。既定は右）で選び、実験的機能のページで六芒星のオーバーレイのスイッチの下に出す。端は作業領域の端（タスクバーの内側）で、六芒星はその中央に出る。
- どのモニターに出すかは設定の`TRAY_COMPANION_MONITOR`で選ぶ。値はシステムがモニターに付けた名前（Windows なら`\\.\DISPLAY2`など）で、空のときは OS のメインのモニターを使う（既定）。実験的機能のページ（端の選択の下）と、トレイのメニューの「六芒星を出すモニター」から選べる。モニターには左から右、上から下の順に番号を付けて見せる。
- 選んだモニターが外されても値は残し、その間はメインのモニターに出す。つなぎ直すと、選んだモニターに戻る。設定ページとトレイのメニューには、接続されていないモニターとして出す。モニターの一覧は、機能がオンの間2秒ごとに読み直し、変わったらトレイのメニューを作り直す。
- 隠れている間は六芒星の窓を出さないので、ゲームのクリックをさえぎらない。Rust 側がポインターの位置を1秒に十数回見て、端の中央付近に近づくと、六芒星の中心を端に置いて半分だけ出す。出すのは、端から約14px以内の帯にポインターが0.16秒とどまったときだけである。帯の中で端との距離が4px（論理）より大きく変わると、待ち時間をはじめから数え直す。隣のモニターとの境目をゆっくり通り過ぎるポインターでは出ない（#563）。窓から離れて約0.45秒たつと、また隠す。窓はフォーカスを取らない。
- 六芒星の6つの三角形はメイン画面の6つのスイッチ（マイク入力、翻訳、読み上げ、ボイスチェンジャー、聞き取り、チャット読み取り）に対応し、メイン画面のスイッチと同じアイコンを描く。オンの機能の三角形は、辺とアイコンを Lilac にし、内側を淡い Lilac で染める（#536）。画面の内側を向いた3つが見えていて、マウスのホイール1段で60°回すと、見える組み合わせが1つずつ入れ替わる。
- 見えている三角形に載せると、その機能の札が画面の中央の方向へ開く。三角形か札を押すと、メイン画面のそのスイッチと同じ切り替えが走る。三角形を押したときは、とどまるのを待たずにすぐ札を開き、何が起きたかを札に出す（#536）。載せただけでは何も切り替わらない。
- 三角形か札を押したあとは、メイン画面がスイッチの状態を返すまで（長くて4秒）、札は「切り替え中…」と出し、三角形も札も押せなくなる。依頼をメイン画面へ送れなかったときは、札が3秒間「切り替えられませんでした」と出す。スイッチがオンやオフに変わると、その三角形が短く光る。メイン画面やホットキーで変えたときも同じである（#536）。
- 六芒星が初めて出たときだけ、ホイールで回すとほかの3つが出ることを、画面の中央の方向に5秒出して知らせる。ホイールを回すか札が開くと、早く消える。知らせたことはメイン画面が設定の`TRAY_COMPANION_WHEEL_HINT_SHOWN`に保存し、次からは出さない。メイン画面が設定を受け取るまでは出さない（#536）。
- 中心の六角形は共通の設定に割り当てる。中心に載せると、共通の設定の札が画面の中央の方向へ開く。中身は六芒星を隠す端の切り替え（`TRAY_COMPANION_EDGE`を保存する）、メイン画面を開く、コントロールパネルを開く、の3つで、どれも押したときだけ動く。中心を押した場合も、コントロールパネルを六芒星のそば（画面の内側）に開く。
- 三角形と中心は、ポインターが約0.18秒とどまったときに札を開く。中心から札へ動かす途中で三角形を横切っても、札は入れ替わらない。
- オフにすると、パネルと六芒星を片付け、トレイのメニューのオーバーレイの項目を灰色にし、隠れていたメイン画面を出す。オフの間はパネルも六芒星も作らず、ポインターも見ない。オーバーレイの命令は断り、トレイのための命令（状態と文言の受け取り、メニューからの依頼の受け渡し）だけを受ける。
- パネルと六芒星にはスイッチの状態と UI の文言だけを渡す。認識した音声や入力した文は渡さず、ログにも出さない。

## 収録先の切り替え通知

`/run/audio_device_switched`はエラーではなく200の状態通知である。UIはマイク・スピーカーごとに変更前後の名前を表示し、既存の警告トーストと同じ時間で閉じる。詳細と互換性は[音声デバイスの選択と識別](data-and-persistence.md#音声デバイスの選択と識別)を参照する。録音の終了時は文字起こしとメーターの状態をそれぞれ通知し、残ったメーター値を消す。
