# ADR-012: Audio AI Runtime Consolidation

Status: 採用（2026-11-17）。開発の原則として定める。既存のコードは変えない。
Date: 2026-11-17
Related: Issue #507、[ADR 001〜003](decisions.md)、[ADR-008](adr-008-external-speech-engines.md)、[core-integration.md](core-integration.md)、`AGENTS.md`、`NOTICE.md`

## 1. 背景

音声 AI のモデルを1つ足すたびに、推論の実行環境（ランタイム）を1つ足すと、次のコストが増える。

- **配布**: ランタイムのライブラリ、GPU 向けのライブラリ、モデルの取得の手順が増え、配布物が大きくなる。何を同梱し、何を同意を得て取得するかを、ランタイムごとに決めることになる。
- **保守**: 版の追従、OS ごとのビルド、GPU の実行プロバイダの組み合わせ、偽物を使った試験を、ランタイムごとに持つことになる。
- **ライセンス**: ランタイムと、それが読むモデルの許諾を、`NOTICE.md` とライセンス台帳で別々に追うことになる。
- **資源**: 同じ PC で VRChat と並べて動かすので、ランタイムごとのメモリ、VRAM、起動の時間が積み重なる。

0.5.0 では Python の実行環境と PyInstaller、CTranslate2、Seed-VC を配布物から外した（`core-integration.md`）。この方向を、新しいモデルを足すときにも保つ。

## 2. 決定

次の原則を採用する（原文のまま）。

> 新しい音声AIモデルの導入は、原則としてspeech.cppへのアップストリーム貢献を優先する。VRCT-VOX固有の推論エンジンや独立したAIランタイムは、既存基盤で実現できない技術的理由と、性能・保守・配布コスト上の明確な優位性が確認された場合に限って採用する。

新しいモデルを入れたいときは、まず speech.cpp に対応を足せるかを調べる。足せるなら、上流に貢献し、アプリは speech.cpp の新しい版を固定して使う。

## 3. 例外を認める条件

VRCT-VOX 固有の推論エンジンや独立したランタイムは、次の2つが**両方とも**確認できたときだけ採用する。片方だけでは足りない。

1. **技術的な理由**: 既存の基盤（4 の分担と、5 の既存の構成）では実現できない理由がある。例として、必要な処理が speech.cpp の設計の範囲外にある、上流が対応を受け入れない、必要な遅延や入出力の形を満たせない、などがある。
2. **明確な優位性**: 性能、保守、配布のコストのうえで、既存の基盤を広げるより明らかに有利である。計測した値には、計測した環境と条件を添える。

例外として採用するときは、ADR を書き、上の2点の根拠と、例外をやめる条件（speech.cpp が対応したら移る、など）を記録する。

## 4. 責務の分担

推奨する分担は次のとおりである。新しい機能やモデルは、この表の担当に載せる。

| 領域 | 担当 |
|---|---|
| 音声 AI の推論 | speech.cpp |
| 画像の OCR | ONNX Runtime |
| ローカル翻訳 | ONNX Runtime |
| 音声の入出力とミキシング | Rust と OS のネイティブ API |
| 音声のリサンプリングとフィルタ | Rust の軽量な DSP |
| UI、設定、VRChat との連携 | VRCT-VOX |

AI の推論は speech.cpp と ONNX Runtime が担い、ほかのランタイムを足すときは 3 の条件で判断する。音声の入出力、ミキシング、リサンプリング、フィルタは Rust と OS の機能で行う。

## 5. 既存の構成の位置づけ

| 機能 | 現在の基盤 | 位置づけ |
|---|---|---|
| ASR（音声認識） | speech.cpp | 中核。4 の分担どおり |
| TTS（読み上げ） | speech.cpp | 中核。4 の分担どおり |
| OCR（チャットの読み取り） | `native/ocr-runtime`（ONNX Runtime、`ort`） | 4 の分担どおり。続ける |
| ローカル翻訳 | `native/translate-onnx`（ONNX Runtime、`ort`） | 4 の分担どおり。続ける |
| RVC（声質変換） | `native/rvc-runtime`（ONNX Runtime、`ort`） | 未決（7 を参照）。決まるまでは今の実装を続ける |

speech.cpp は ASR と TTS の中核である。新しい ASR や TTS のモデルは、まずここに載せる。

OCR と翻訳は speech.cpp の扱う範囲の外にあり、ONNX Runtime を使ってきた（翻訳は `core-integration.md` の比較）。

RVC は声を扱う AI の推論なので、4 の表では speech.cpp の担当に入る。一方で、今の実装は ONNX Runtime の上にある（声質変換の選定は ADR 003 以降）。理由のある既存の例外として ONNX Runtime で続けるのか、将来の移行先を speech.cpp とするのかは決めていない。

OCR、翻訳、RVC の3つとも同じ版の `ort` を通して ONNX Runtime を使い、ランタイムの種類は1つに揃っている（OCR と翻訳は同じプロセスで1つのライブラリを共有し、RVC は別プロセスの worker で読み込む）。この ADR はこれらを置き換えも削除もしない。ただし、ONNX Runtime 系に新しいモデルを足すときも、2 と 3 の考え方で判断する。

## 6. 結果

- 新しい音声 AI モデルの提案は、speech.cpp への貢献の可否を調べた結果から始める。
- 新しいランタイムを足す提案には、3 の2つの条件の根拠が要る。
- 上流への貢献が増えるので、上流の受け入れを待つ時間が機能の時期に影響することがある。

## 7. 未決のこと

- RVC（声質変換）の位置づけ。4 の分担では音声 AI の推論は speech.cpp の担当で、ONNX Runtime の行に RVC はない。今の RVC は ONNX Runtime の実装なので、理由のある既存の例外として続けるのか、将来の移行先として speech.cpp を示すのかを決める。決まるまでは今の実装を続ける。
- 利用者が自分で入れた外部のエンジン（ADR-008 の VOICEVOX など）にループバックで接続する方式が、この原則の「独立した AI ランタイム」に当たるか。アプリは同梱も起動もしないので当たらないと読めるが、明記していない。
- 3 の「明確な優位性」を、どの指標（遅延、配布物のサイズ、VRAM など）で、どれだけの差があれば認めるか。
