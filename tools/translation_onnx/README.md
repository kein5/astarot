# ONNX 版ローカル翻訳モデルの作成と比較

`native/translate-onnx` が読み込むモデルを作り、現行の CTranslate2 と訳文を比べるための道具です。アプリの実行時には使いません。

## モデルを作る

```sh
uv venv --python 3.11 build/translation-onnx/venv
uv pip install --python build/translation-onnx/venv/bin/python --index-strategy unsafe-best-match \
    --extra-index-url https://download.pytorch.org/whl/cpu -r tools/translation_onnx/requirements.txt
build/translation-onnx/venv/bin/python tools/translation_onnx/export.py m2m100_418M --output <出力先>
```

`<出力先>/m2m100_418M-onnx-int8/` に、エンコーダとデコーダの ONNX、語彙の行列（`vocabulary.data`）、`tokenizer.json`、`vocab.json`、`manifest.json` ができます。`manifest.json` には、各ファイルの SHA-256、元のモデルのコミット、使ったパッケージの版が入ります。

グラフは `torch.onnx.export` で書き出します（`graphs.py`）。

- 各層の重みはモデルのものをそのまま使い、つなぎ方だけを `graphs.py` に書いています。デコーダのキャッシュは、テンソルで受け渡します。
- 量子化の前に、transformers 本来の計算と照合します。対象は、エンコーダの出力と、デコーダの初回とキャッシュ付きの各ステップの logits です。最大の誤差は `manifest.json` の `verified_max_difference` に入ります。
- 2つのデコーダ（初回とキャッシュ付き）は量子化してから、`use_cache_branch` で切り替える1つのグラフにまとめます。両方にある重みは1つにします。
- 語彙の大きさの行列（エンコーダの埋め込み、デコーダの埋め込み、出力層）は、量子化すると同じバイト列になります（出力層は転置）。そこで、`vocabulary.data` に1回だけ置き、両方のグラフから外部データとして読みます（`graphs.share_vocabulary`）。
  - 出力層は埋め込みの転置（Transpose）です。ONNX Runtime が読み込むときに定数へたたみ込むので、行列積は整数の MatMulInteger のままです。
  - バイト列が一致しないときは止めます。まとめる前と後で、照合用の入力に対するエンコーダの出力と各ステップの logits が完全に一致することも確かめ、違えば止めます。
- 以前は optimum を使っていましたが、やめました。optimum-onnx のどの版も、既知の脆弱性が直った transformers（5.10 以上）に対応していないためです。
- M2M100 の `tokenizer.json` は、SentencePiece のモデルから直接組み立てます。transformers 5 系の変換器は、BPE 型のモデルで失敗するためです。結果は、transformers 4.57 の変換器で作ったものとバイト単位で同じです。

- 元のモデルは `export.py` の中でコミットを固定しています。
- 必要なメモリの目安は、418M・600M が 15GB、1.2B・1.3B が 30GB、3.3B が 55GB 程度です。中間ファイルも元のモデルの数倍の大きさになります（3.3B では約 27GB）。tmpfs の `/tmp` ではなく、ディスク上を `--work` に指定してください。量子化も数 GB の一時ファイルを作るので、大きいモデルでは環境変数 `TMPDIR` もディスク上に向けてください。
- `--float32` を付けると、量子化しないモデルを作ります。これはデコードの検証用で、アプリでは使いません。

## 現行の CTranslate2 と比べる

比べるときの Python 環境は、アプリの `uv.lock` と同じ版にします（ctranslate2 4.8.4、transformers 5.22.1、tokenizers 0.23.3、sentencepiece 0.2.1）。これに sacrebleu 2.6.0 を足します。

```sh
cargo build --release --manifest-path native/translate-onnx/Cargo.toml
python tools/translation_onnx/compare.py m2m100_418M \
    --onnx <出力先>/m2m100_418M-onnx-int8 \
    --cli native/translate-onnx/target/release/vrct-translate \
    --out <結果>.json
```

CTranslate2 の側は、アプリが固定しているモデルを取得し、ピン留めと照合してから、`translation_translator.py` と同じ手順で翻訳します。比べる対象は、WMT20 の8方向（英語と日本語・中国語・ドイツ語・ロシア語の双方向）で、各方向の先頭 N 文です。結果のファイルには点数と件数だけを書き、文章は書きません。

`--directions en-ja,ja-en` のように指定すると、方向を絞れます。

## 保存のしかたを変えたときの回帰確認

モデルの保存のしかた（重みの置き方や圧縮）を変えたときは、変える前のバンドルと訳文が変わらないことを `regression.py` で確かめます。CTranslate2 は使わず、sacrebleu だけで動きます。

```sh
python tools/translation_onnx/regression.py \
    --cli native/translate-onnx/target/release/vrct-translate \
    --before <変える前のバンドル> --after <変えた後のバンドル> --sentences 100 --out <結果>.json
```

比べる文は `compare.py` と同じ（WMT20 の8方向の先頭 N 文）です。方向ごとに、出力のトークン ID が一致した文の数、それぞれの失敗の数、参照訳に対する BLEU と chrF を書きます。すべての文で ID が一致したときだけ、終了コードが 0 になります。

## 比較の結果（2026-11-15）

結果のファイルは `results/` にあります。モデルは `graphs.py` で書き出したもの（transformers 5.22.1、optimum なし）です。

- 環境：Linux x86_64（Ryzen 9 9900X）の CPU。スレッドは4つで、CTranslate2 の計算型は int8 です。
- CTranslate2 の側は、アプリが固定しているモデルを、アプリと同じ版（ctranslate2 4.8.4、transformers 5.22.1）で動かしました。CTranslate2 側の点数は、どのモデルも前回の比較と完全に同じでした。
- 比べた文は、WMT20 の8方向それぞれの先頭の文です。418M と 600M は各方向 100 文、ほかは 50 文です。
- 方向をいくつかの区切りに分けて並行して走らせ、あとで合わせました（`runs` の欄に記録があります）。
- 比べた ONNX 版は、語彙の行列を1つにまとめる前のものです。まとめた後のモデルは、同じ文のすべてで同じ出力 ID を出すので（下の「取得量の対策」）、この結果は今のモデルにもそのまま当てはまります。

### int8 どうしの比較

| モデル | 文数 | BLEU の差（平均） | chrF の差（平均） | 訳文の完全一致 | 入力 ID の不一致 | 失敗（CT2 / ONNX） |
|---|---|---|---|---|---|---|
| M2M100 418M | 800 | +0.14 | +0.06 | 326 | 0 | 0 / 0 |
| M2M100 1.2B | 400 | +0.35 | +0.23 | 154 | 0 | 0 / 0 |
| NLLB 600M | 800 | -0.06 | -0.11 | 244 | 0 | 1 / 1 |
| NLLB 1.3B | 400 | -0.07 | -0.22 | 171 | 0 | 0 / 1 |
| NLLB 3.3B | 400 | -0.58 | -0.18 | 149 | 0 | 0 / 0 |

差は「ONNX − CT2」で、どちらも参照訳に対して測りました。デコードの不一致（ONNX の出力 ID をアプリのトークナイザで戻した文字列と、ONNX の訳文の違い）は、どのモデルでも 0 です。

- **失敗**は、どれも 256 トークンまでに終了トークンが出なかったものです。アプリが CTranslate2 で失敗として扱う条件と同じです。量子化の方式の違いによって、繰り返しに入る文が変わります。比較では失敗を空の訳文として数えるので、1文で BLEU が数点下がることがあります。NLLB 1.3B の zh→en（-3.32）がその例です。
- **NLLB 3.3B** は、英語へ訳す4方向がすべてマイナスでした（BLEU -1.12〜-1.90）。optimum で書き出した前回も同じ傾向でした。各方向 50 文なのでぶれは大きいですが、回帰がないとまでは確認できていません。

### float32 どうしの比較（探索の確認）

量子化しない M2M100 418M で、ONNX と CTranslate2（元のモデルを float32 で変換したもの）を比べました。**400 文中 399 文で訳文が完全に一致しました。** 残る1文（de→en）は、float32 の丸めの違いで同点に近い候補が入れ替わったものです。int8 で出る差は、探索ではなく量子化の方式（CTranslate2 の int8 と ONNX Runtime の動的 int8）によるものだと言えます。

### 速度（参考）

| モデル | 方向（30 文） | CT2 | ONNX |
|---|---|---|---|
| M2M100 418M | en→ja | 27.5秒 | 40.5秒 |
| M2M100 418M | ja→en | 10.0秒 | 12.1秒 |
| NLLB 600M | en→ja | 18.3秒 | 20.4秒 |
| NLLB 600M | ja→en | 10.5秒 | 11.0秒 |

- 計測の条件：同じ PC の CPU で、スレッドは4つです。ほかのセッションの処理で平均負荷は 1〜4 ありました。
- ONNX の時間には、コマンドの起動とモデルの読み込みも含みます。
- CPU では、ONNX のほうが 1.05〜1.5 倍遅くなりました。GPU（DirectML）では計っていません。

### モデルの大きさ

| モデル | CT2 版 | ONNX 版（まとめる前） | ONNX 版（今の形） |
|---|---|---|---|
| M2M100 418M | 500 MB | 768 MB | 506 MB |
| M2M100 1.2B | 1,259 MB | 1,527 MB | 1,265 MB |
| NLLB 600M | 647 MB | 1,168 MB | 643 MB |
| NLLB 1.3B | 1,401 MB | 1,927 MB | 1,402 MB |
| NLLB 3.3B | 3,379 MB | 4,429 MB | 3,380 MB |

まとめる前の ONNX 版が大きかったのは、語彙の大きさの行列を3つ持っていたためです（エンコーダの埋め込み、デコーダの埋め込み、出力層）。

- 量子化の前に出力層を埋め込みと共有させると、量子化で整数の行列積にならず、毎ステップ語彙の行列を float に戻すので、3倍ほど遅くなります。そこで `graphs.py` は出力層に専用の重みを持たせ、`check_quantized` がそうなっていないグラフを止めます。
- 量子化した後の3つはバイト単位で同じなので、`vocabulary.data` に1回だけ置きます（「モデルを作る」の節）。これで CT2 版とほぼ同じ大きさになりました。

## 取得量の対策（2026-11-15）

ONNX 版のモデルの取得量を減らす方法を3つ比べました。受け入れの物差しは「対策の前後で訳文が同等であること」で、上の比較と同じ文（418M と 600M は各方向 100 文、ほかは 50 文）で確かめました。

| 方法 | 種類 | M2M100 418M | NLLB 600M | 訳文 | 扱い |
|---|---|---|---|---|---|
| 語彙の行列を1つにまとめる | 可逆 | 768 → 506 MB（-34%） | 1,168 → 643 MB（-45%） | 5モデルの全文（2,800 文）で出力 ID が一致 | **採用** |
| 配布するファイルを zstd -19 で圧縮する | 可逆（転送だけ） | 506 → 416 MB（-18%） | 643 → 480 MB（-25%） | 変わらない | 未実装 |
| 層の重みを 4bit にする | 非可逆 | 506 → 374 MB（-26%） | 643 → 511 MB（-21%） | 一致は 418M で 156/800 文、600M で 97/800 文 | 不採用 |

- **語彙の行列を1つにまとめる**：結果は `results/vocabulary-shared/` にあります（`regression.py` の出力）。1.2B は 1,527 → 1,265 MB、1.3B は 1,927 → 1,402 MB、3.3B は 4,429 → 3,380 MB です。3.3B も外部データのファイルが要らなくなりました。
  - 速度は変わりません（この節の最後の表）。出力層は埋め込みの転置で、ONNX Runtime が読み込むときに定数にするので、行列積は今までどおり整数で計算します。メモリの最大使用量（`vrct-translate` で 1 文訳したときの VmHWM）は、418M で 1.38 GB から 1.12 GB に減りました。
- **zstd -19**：モデル自体は変わりません。ただし、取得する側に展開の処理と、圧縮後のファイルのサイズと SHA-256 の固定が要ります。モデルの配布先と取得カタログを決めるときの選択肢として残します。
- **層の重みを 4bit にする**：418M と 600M で作った一度限りの試作で、道具には入れていません。
  - 設定：エンコーダとデコーダの各層の行列積を、ONNX Runtime の `MatMulNBits`（4bit、32 個ごとのブロック、対称、accuracy level 4）にしました。出力層と埋め込みは int8 のままで、語彙の行列もまとめています。
  - 訳文：int8 と出力が一致した文は 418M で 156/800、600M で 97/800 でした。参照訳に対する BLEU の差は、418M が平均 -0.39（方向ごとに -1.16〜+0.33）、600M が平均 -1.10（-2.63〜+0.10）です。600M では失敗が 1 文から 2 文に増えました。
  - 受け入れの物差し（訳文が同等）を満たさないので、採りません。さらに小さくしたい場合は、この品質の差を受け入れるかどうかの判断が要ります。

### 語彙の行列をまとめる前と後の速度

30 文で測りました。結果は `results/vocabulary-shared/speed/` にあります。

| モデル | 方向 | まとめる前 | まとめた後 |
|---|---|---|---|
| M2M100 418M | en→ja | 42.5秒 | 42.5秒 |
| M2M100 418M | ja→en | 12.0秒 | 11.9秒 |
| NLLB 600M | en→ja | 19.9秒 | 19.7秒 |
| NLLB 600M | ja→en | 10.9秒 | 10.9秒 |

- 同じ PC の CPU で、スレッドは4つです。ほかのセッションの処理で、平均負荷は 2.6〜3.1 ありました。
- 順番の影響を除くため、前と後の順を入れ替えて2回ずつ測り、平均しました。時間にはコマンドの起動とモデルの読み込みも含みます。
- 30 文はすべて同じ出力 ID でした。
